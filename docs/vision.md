# lane-router 的北极星：持续自主推进的 agent 群体

> **草稿**，2026-10-20 由 `lane-router/design` 起。愿景是用户的：第一节全部是用户原话（标出处），第二、三、四节是 design 草拟的结构，**措辞由用户定**。缘起：Company 产品停投（问答 `b8551555`，Vikunja LR-20），把愿景从 Company 仓的历史文件夹搬到活的地方，免得仓一停、愿景跟着埋。

## 一、愿景（用户原话）

2026-10-10（Company 仓 `docs/project-history/records/holon/owner-vision-20261010.md:9-10`）：

> 我的愿景是，做一个能持续自主推进的agent group系统一样的东西。在现实生活中company是最常见的满足这个需求的一个组织，所以我选了这个。
> 至于你问我具体的需求，那我现在有几个具体明确的需求：一个就是开一个company做我的心理咨询和健康管理的教练的角色；还有一个是帮我去调研并且自己赚钱的company，这个我很好奇他能做成什么样子；还有就是比较传统的帮我开发一个项目或者软件。

同日补充（`:24`）：

> 就在我的认识里，company是一个类似于形式系统的东西，他可以承载各种各样的内容。

经市场 lane 转交的原话（`:30`；记录者注明未亲见原始聊天）：

> 我希望agent帮我主要是管理我的生活，帮我持续推进任务（可能很久一直跑不需要我管的这种）。不能接受的限制就是需要我持续推进。此外效率下降的很离谱也不能接受。

2026-10-20，用户对「最初愿景」的复述（问答 `b8551555` 第 17 条）：

> 我如果只给一个高层目标，和少量指导和决策，能不能让一群agent帮我持续推进一个愿景

2026-10-20，现状（同议题第 14 条，用户三条回答，原话）：

> 1. lane-router做的最好的就是这个router功能，让我从一个agent变成了现在我能指挥数十个agents协同工作。没什么让我手工传上下文的事情了。
> 最近的一个痛点是很多时候我要给在做heavy work的lane对话，然后我也有事，等我来看回复的时候回复已经刷走了，所以我就做了这个问答，也很好用。而且我意识到有了这个问答我就跟agent对话解耦了，可以一个lane推进多个事项（虽然我不确定这个是不是好的做法）
> 2. 持续自助推进我觉得lane做的还不错。我上周末让mayacustomnodes那边的lane让我调研UE原型，完成的质量和结果我觉得就不错。最开始我的company只是一个想法，就是让agent给我长期推进，我只给高层指令和必要的介入。但是实现中从来没有做出来一个让我满意的产品出来。
> 3. 我觉得现在没有什么我要人肉记得事情了，至少目前没有了。我们引入问答和vikunja之后这个已经好很多了。而且现在开始引入图和知识库了，已经快开始慢慢长成company的雏形了我觉得？

## 二、「做到了」长什么样（design 草拟的判据，不是功能表；请改）

从上面的原话里抽出来、可观察的：

1. **用户只给高层目标和必要决策。** 衡量：一段时间里用户介入的次数和种类——决策、催办、传上下文分开数；「催办」和「传上下文」应趋近于零（现状：用户说已经没有了）。
2. **一群 agent 跨日、跨会话持续推进。** 衡量：一项跨日任务在没有用户输入的情况下接着干——换代后、恢复后不停摆。现状：周末 UE 原型调研是一个数据点；恢复后自动接活正在修（LR-25 重通知、LR-18/19 lane 自主性）。
3. **用户能看见「需要我处理什么 / 正在做什么 / 谁在干什么」，不用翻窗口。** 现状：问答「待我处理」、看板、`lane_directory`、Vikunja——分散在几处。
4. **效率不离谱地掉。** 衡量：单条 lane 上下文过载前能自己换代；用户不用为了系统本身做平台工作（Company 的教训：`lessons.md` 第 7、8 条）。
5. **用途不限于编码。** 健康教练、调研 / 赚钱是原始用例；目前只有软件开发在 lane-router 上验证过。记在这里是为了不忘，不是为了现在做。
