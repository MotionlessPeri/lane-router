# 图资源接入需求与方案方向

状态：用户已确认第一版使用流程与图模型，并于 2026-10-19 允许删除节点和关系、要求直接开始实现。按第 5 节同进程独立模块方向执行；实现与本地验证已授权，共享 Router 部署或重启仍交外部维护对话。

## 1. 目的与第一版流程

用户在已有 lane 对话中围绕一份图讨论，由 lane 使用工具读取、创建或修改图；用户通过网页查看保存后的图，再回到 lane 继续讨论。

第一版从 lane 发起：

1. 用户在 lane 对话里要求新建或打开一份图。
2. lane 取得资源引用，使用图工具读取当前内容。
3. 需要修改时，lane 申请该资源的写锁，取得锁后重新读取最新内容，再修改和保存。
4. lane 提供该图的网页查看链接。用户打开网页浏览图，并在原 lane 继续讨论。

这里的“网页查看入口”与“从图发起讨论”是两件事。第一版保留前者，不提供从图页面选择 lane、发送消息或发起新讨论的入口。

## 2. 已确认需求

### R1：图作为独立资源存在

图有自己的身份、内容和保存位置，独立于 lane。资源插件不规定资源只能归属一个 lane，也不因某条 lane 结束而隐含删除资源。同一份图可供多个 lane 访问，一个 lane 也可以访问多份资源。

如上层产品需要限制资源访问或归属，由上层决定；本轮不增加独占归属规则或访问授权管理功能。

### R2：资源类型提供适合自身的 agent 工具

用户要求 lane 具备资源访问能力，不同种类的资源提供不同工具。第一版的具体资源类型是图，工具支持上述创建、打开、读取和更新流程。其他资源类型、通用资源管理界面及插件运行平台不在本轮实现范围内。

图工具需要让 lane 取得实际保存内容，并将修改写回该资源。只在答复中生成一份图描述、只给网页显示模拟数据，均不满足此需求。工具名称、参数、图数据结构与操作粒度在技术设计中确定。

### R3：多个 lane 可读写，写入采用资源级长写锁

读取可以并行；同一资源同一时刻只有一个写入者。用户接受其他写入者等待，第一版按整份资源加长写锁，不按节点分别加锁，也不采用基于图内容版本号的提交冲突流程。

lane 在一轮修改前申请锁，持锁后重新读取当前内容，修改结束后主动释放。持锁期间其他 lane 仍可读取已保存内容，其修改等待锁可用。具体等待通过短请求重试还是其他方式完成，留到技术设计，不因“可以等待”而预设长时间挂起工具调用或新增持久排队系统。

用户可以查看持锁者并在异常时强制解锁；强制解锁后，旧持锁凭据立即失去写入能力。所有图写入口使用同一锁规则。锁的保存方式、会话轮换及进程重启后的处理需要在技术设计中落实，不能把临时持锁解释成资源所有权。

### R4：讨论在 lane 侧进行

每条 lane 使用自己的对话上下文，不把多个 lane 的讨论合并成图的公共讨论区。资源引用说明讨论的是哪份图，不因此给图增加独立会话或对话生命周期。

第一版由用户在 lane 对话中开始和继续讨论。lane 读取资源后执行已授权的修改，再反馈结果。

### R5：网页只用于查看图

图网页提供图的展示与浏览，包括缩放、子图导航、选择节点和查看详情。第一版没有图内讨论区、选择 lane 发起聊天、消息输入或图内容编辑功能。

网页读取与 lane 操作对应的已保存图内容。网页刷新后仍可查看已保存结果，不要求用户保持原型页面打开。现有演示中的浏览器本地草稿不能直接作为 lane 共享读写的权威记录。

第一版不承诺自动实时推送；刷新即可看到已保存结果。是否需要更即时的更新由后续体验决定。

### R6：议题收件箱是可独立使用的讨论入口

用户提出可以考虑借用 coordinator 正在做的“lane 注册问题”功能。现有[用户议题收件箱需求](2026-10-17-user-issue-inbox-requirements.md)支持 lane 从 TUI 发布议题，随后用户在已有议题中继续问答；第一版不从网页主动新建议题。

当前最小复用方向是议题正文附图 URL 文本，讨论继续使用该议题原有规则。议题正文目前通过 `textContent` 展示，没有 Markdown 或链接自动识别，用户需要复制 URL 打开；不能把附 URL 文本描述成已实现可点击图链接、图嵌入或图讨论入口。图查看和图工具的第一版流程不依赖议题功能；不为此要求议题模块增加资源表、专用图字段、从图创建议题或新的消息入口。

议题代码已本地整合至 `254cd0e8a69487bd5cece5aa69fb42f81af1bcb0`，实现位于 `src/modules/issues` 与 `src/ui/issues/index.html`，使用及现场验收见[手工验证文档](../../manual-tests.md)。coordinator 回报真实浏览器、真实客户端工具刷新与模型往返、部署重启尚未验收；本稿的源码核对不改变这一状态。

### R7：普通节点关系与可选分组

用户认可正式图模型使用普通节点与关系，并提供可选分组。知识图可以按组收起、展开，跨组关系仍保留；项目类关系图可以直接使用没有分组的普通关系网，不强制套用演示中的“领域／主题／概念”三层。具体字段和分组约束在技术设计中确定。

### R8：支持基本删除

用户已允许 lane 删除节点和关系。删除使用同一写锁和原子批次；删除节点时须在同一批中显式移除或改指其关联关系，否则整批拒绝，避免自动连带删除与悬挂引用。首版不删除整份图或分组，不提供历史回滚。

## 3. 第一版验收场景

| 场景 | 用户应看到的结果 |
|---|---|
| 用户在 lane 里要求创建一份知识图 | lane 创建实际资源，返回可继续访问的引用和网页查看链接 |
| 用户要求修改一份已有图 | lane 读取该图，取得写锁并重读后修改；网页刷新可看到相同的已保存内容 |
| 另一条 lane 打开同一份图 | 能读取相同资源，无需复制一份图或变更资源所有者 |
| 两条 lane 都需要修改同一份图 | 一条持锁修改，另一条等待；后者拿锁后读取前者已保存的结果 |
| 一个 lane 长时间讨论或执行修改 | 写锁可跨工具调用持有，其他写入者等待；已保存内容仍可查看 |
| 持锁者异常，需要用户接管 | 用户能识别持锁者并强制解锁；旧凭据后续写入被拒绝 |
| 用户关闭图网页，再次打开链接 | 可以读取资源的已保存内容；图不依赖浏览器页面维持 |
| 用户希望继续讨论图中的关系 | 回原 lane 对话讨论；图页面没有聊天入口 |
| 某段相关讨论已发布到议题收件箱 | 可在该议题原有入口继续问答，复制正文的图 URL 查看图；不改变议题归属及生命周期 |
| lane 创建项目类关系图或带分组的知识图 | 无分组图可直接浏览；有分组时可收起、展开，跨组关系仍保留，不强制要求三层 |
| lane 删除错误关系，或在一批中删除节点及其关系 | 同一锁下完整保存；漏处理关联关系时整批失败，其他内容不变 |

本轮采用同一可信机器上的常规 lane 和本地查看网页，不新增远程访问、多用户账户、细粒度授权、自动唤醒或 lane 创建入口。受限外部 Host 的工具开放范围另行确认，不因资源工具存在就宣称已兼容。

独立图原型已选 React Flow，原型目录为 `D:\my_projects\lane-router-graph-ui-prototypes`，学习工作台交付提交为 `9966e7b`。它证明了图的显示、局部导航、避让及编辑体验可行，但尚未实现 Router 资源接入。原型的内容编辑、浏览器自动保存和撤销能力不等于本轮查看网页必须包含这些功能。

主仓截至 `254cd0e8a69487bd5cece5aa69fb42f81af1bcb0` 的相关事实：

- `src/application/tool-catalog.ts` 已实现工具定义集合、参数解析与绑定，`src/application/builtin-tools.ts` 已显式组合通信工具和议题工具。图工具应接入这套装配方式及实际调用入口，不能只增加一个定义就宣称 agent 已可调用。
- `src/process/dashboard-http.ts` 已把后台 HTTP 展示和动作适配与通信核心分开。

## 5. 接入方向

下面比较满足同一条第一版流程的方案。用户要求开始后，按同进程独立模块方向实施，详见[技术设计](2026-10-18-graph-resource-design.md)和[实施计划](../plans/2026-10-19-graph-resources.md)。

| 方向 | 主要收益与代价 | 当前建议 |
|---|---|---|
| 同进程内置资源功能模块，先实现图类型；工具和查看网页通过同一图服务读取保存内容 | 复用 Router 现有身份和工具入口，内容与锁在服务侧统一；需要接上工具组合及前端静态资源构建 | 推荐进入详细设计 |
| 独立图服务，Router 工具通过新的服务接口访问 | 部署和运行可独立，但第一版额外引入进程、服务连接与管理 | 当前流程不需要，不选 |
| lane 直接编辑图文件，网页单独读取文件 | 文件容易查看，但跨 lane 的锁、校验和网页读取仍需统一实现；各 agent 直接写文件会绕过工具规则 | 不作为第一版接入方案 |

推荐方向中的职责草案：

- 通信核心继续管理 lane 身份、绑定与通信，不保存图节点、关系或图的业务锁。
- 资源功能模块管理本轮图资源的身份、保存、长写锁和图操作，向 agent 提供图类型工具。
- 网页用 React Flow 展示服务返回的图，承担浏览状态，不承担资源权威保存。
- 应用入口装配资源模块的服务、工具与 HTTP；与议题模块共享已确定的宿主装配方式，业务互不依赖。

第一版可以在一个独立功能模块内实现这些职责。当前没有第二种具体资源类型，不提前规定通用适配器基类、动态插件发现或多种存储后端。不同类型各自提供工具的需求保留在装配边界中。

基线是第 1—3 节的已确认用户流程。以下候选只说明详细设计可能需要的表面，不是批准实施或新增实现计划。

| 候选 | 消费者与频率 | 需求依据 | 删除后果 | 既有替代 | 处置 | 关闭条件 |
|---|---|---|---|---|---|---|
| 图资源身份与保存内容 | 多条 lane、查看网页，正常路径 | 明确：R1、R2、R5 | 无法稳定打开同一份图或查看已保存结果 | 演示 JSON 及浏览器草稿缺少共享业务写入口 | 保留行为；存储方案待设计 | — |

本次从原型范围增加的是 lane 操作实际共享资源、统一长写锁和只读查看网页。相对早期口头设想，第一版已收窄为 lane 发起，取消图页发起讨论及图内聊天；没有增加临时验证入口或新部署方式。
