# lane set：把一起干活的 lane 开进同一个窗口 —— 需求确认稿

**状态：** 需求确认稿，2026-10-16 与用户对话逐条确认。**只写要什么，不写怎么做**；设计另起一稿，以本文「不做」一节为约束。

## 一句话

> 今天一个项目的所有 lane 共用一个 Windows Terminal 窗口，别的分法只能手拖标签页。用户要的是：把「现在一起干的那一批 lane」开进同一个窗口，这批可以是一个项目的子集，也可以跨项目。

## 术语表

| 词 | 含义 |
|---|---|
| set | 一组 lane 的名字加成员表。Router 自己存的数据，lane 身上不加字段 |
| 默认 set | 没进任何 set 的 lane 按项目归堆。它不是一条数据，只是「没有 set」时的行为 |
| 窗口 | Windows Terminal 的一个窗口，lane 作为标签页开在里面。Router 开 lane 时用 `-w <名字>` 指定 |
| 启动器 | 后台页面上用来勾选并启动 lane 的那一块 |

## 现状（2026-10-16 实测）

- 窗口名等于项目名。`src/process/terminal-spawn.ts` 的 `childEnvironment` 把调用方传来的 `window` 放进 `LANE_ROUTER_CHILD_WINDOW`，三个调用方（启动 `lane-launcher.ts`、恢复 `conversation-restorer.ts`、轮换 `rotation-launcher.ts`）传的都是 lane 的项目。
- 启动器页面两层：项目 → lane，两层都按首字母排（2026-10-16 起）。每条 lane 后面跟着 backend、恢复状态、model；用户说这些他不看。
- 在用库 58 条 lane、26 个项目。用户要分组的实例：
  - `mayacustomnodes` 15 条，天然四堆：代码调研六条（`research-lead` / `engine` / `gpu` / `maya` / `infra` / `ue`）、授权与离线三条、Linux 两条（在虚拟机上，本来不开本机窗口）、常驻四条。用户点名要的是「调研六条新开时也在一起」。
  - 跨项目一：开发 curvenet 的 Maya 侧时，`curvenet_core/dev` 和 `curvenet_maya/dev`、`curvenet_maya/hub` 是一件事。`curvenet_core` 是 submodule 单独立的项目。
  - 跨项目二：`mocap/app` `hub` `design` 加 `of_retarget_kit/hub` 加 `of_dcc_base/hub`，五条 lane 的角色互相点名，三个项目实际是一棵 app 树加两个 submodule。
- 跨项目的需要不是偶发：项目边界跟着仓走，活跨仓。只要 submodule 单独立项，这种 set 就会再出现。

## 已确认的需求

1. **set 是独立对象。** 有名字、有成员表，Router 持久保存，可以改成员。lane 自己不带「属于哪个 set」的字段。
2. **一条 lane 最多在一个 set 里。** 挪到别的 set 就是从原 set 里拿出来。
3. **默认 set 不落数据。** 没进 set 的 lane 一切照旧：窗口名是项目名，页面按项目列。不建 set 的项目什么都不变。
4. **set 可以跨项目。** 后果用户接受：`of_dcc_base/hub` 进了 mocap 的 set，`of_dcc_base` 项目的窗口就空了；一条 lane 只能出现在一个地方，将来一条 lane 同时服务两件事就得选边（今天的 lane 里没有这种情况）。
5. **窗口按 set 开。** 从启动器新开、恢复、轮换时，lane 有 set 就进 set 名的窗口，没有就进项目名的窗口。
6. **set 在页面最上面，然后才是按项目列的 lane。** 启动器里 set 组全部排在项目组前面，建 set 的控件也在最上面；跨项目的 set 用 set 名显示，里面的 lane 带项目前缀；没进 set 的 lane 按项目名分组排在后面。lane 行保持原样（地址 · backend · 恢复状态 · model）。
   > 勘误（2026-10-16）：本条原写「lane 行只要名字，那一串用户不看」，是把用户说的「lane 后面的东西不看」（指启动器下面的积压队列、lane 拓扑、消息流几节）错当成了每条 lane 后面那串，未经确认就写进来，实现后被用户指出。已改回。
7. **建 set、挪 lane 在页面上做。** 这就是用户今天手拖标签页那个动作的替代。
8. **set 不带生命周期。** 不随 campaign 一起开、一起归档；归档仍按 lane。
9. **先做 Router 内部数据，不与 Vikunja 联动。** 澄清下来两边的轴不一样：Vikunja 子项目在项目之内、记需求；set 可跨项目、记「现在一起干的那一批」。以后有需要再接。

## 不做（方案必须守的）

- 地址 `project/lane` 不变。set 不进地址、不进 mailbox 目录、不进消息格式。
- `lane_directory`、`lane_restore_project` 仍按项目查、按项目恢复。要不要加按 set 的查询和恢复，进入方案阶段再答。
- 不做「整个 set 一键打开 / 一键归档」。顶多是以后的便利，不是概念的一部分。
- 不用 Vikunja 子项目当 set 的来源或落点。
- 虚拟机上的 lane 不由 Router 开窗口，set 对它只影响页面分组。

## 待讨论的问题（进入方案阶段再答）

1. set 名的约束：要能当 Windows Terminal 的窗口名；和项目名撞名怎么办。
2. 页面上建 set、挪 lane、删 set 的具体交互。
3. 改了 set 之后，已经开着的窗口要不要跟着挪，还是只影响之后开的。
4. 恢复（`lane_restore_project` 和页面上的「恢复 lane」）按项目还是按 set。
