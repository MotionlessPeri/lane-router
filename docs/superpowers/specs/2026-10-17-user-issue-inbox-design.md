# 用户议题收件箱：模块、接口与可靠投递设计草案

状态：用户于 2026-10-18 确认整体设计，已进入[实施计划](../plans/2026-10-18-user-issue-inbox.md)编写阶段；本稿不包含实现、真实模型测试、构建在用产物或部署授权。

需求依据见[需求确认稿](2026-10-17-user-issue-inbox-requirements.md)。除第 2、5 节明确标为已实现的通信能力外，本文的模块、类型、表和入口仍是拟定设计。用户已选择[浏览器样稿](../mockups/issue-inbox-layout-browser.html)中的“列表与详情”布局，样稿不连接真实后端，不代替功能实现或验收。

## 1. 设计结论与确认范围

已确认：议题归 lane；通信 core、议题模块和 UI 分层；同进程显式装配；各模块拥有自己的表与读写规则；工具与 HTTP 调用同一业务服务。core 不承担议题规则，UI 不承担权威保存。

推荐的具体方案：

- 使用现有技术栈与 Router 进程，不引入新的服务、网络 MCP server 或消息中间件。
- 议题模块使用独立 SQLite 文件，业务表也与 core 分离。用户在了解跨库关联的能力与代价后正式确认双库，见第 3 节。
- 模块提供服务、工具定义、HTTP 适配和持久待投递记录；应用入口装配。只需要通信的产品不装配这些部件。
- 新工具复用既有工具接入；为不能获得新动态工具的旧 Codex 会话提供 CLI 兼容入口。入口不复制业务逻辑。
- 回复先在议题库保存，再经 core 入箱。系统分别报告保存、入箱和 agent 处理事实，不宣称业务动作恰好执行一次，也不增加通知/ACK 状态查询接口。

用户已确认的“结束”边界：结束后拒绝新的讨论追加，已经保存的记录保留，不增加专门的迟到回复功能。结束不隐含取消已经授权的任务；并发与重试细则见第 8 节。整体设计现已获确认，不等于尚未审阅的实施计划或功能交付结果已获批准。

## 2. 当前实现与复用依据

| 当前代码事实 | 对设计的影响 |
|---|---|
| `src/router/types.ts` 的 lane 有稳定 `id`，地址归档后可复用 | 议题存 `owner_lane_id`，地址只作显示，不能靠地址把旧议题转给新 lane |
| `RouterCore.send` 要求发送方是已绑定 lane；`src/router/user-message.ts` 已定义 `UserMessageDelivery`，由 `RouterCore.deliverUserMessage` 实现 | 议题回复直接复用进程内通用投递接口，使用稳定 lane ID、固定来源、完整正文和持久请求键，不再重复抽取发送流水线 |
| `TellAdapter` 已把主题校验及“准备后等待用户回 TUI”模板留在旧入口；通用接口不包含这些规则 | 保持旧 CLI、HTTP 和结果兼容；看板不调用专用 `tell`，不要求用户回复后回 TUI 重复 |
| 通用投递已有同键重试、孤立文件恢复和归档后查询原结果的测试；结果仅含 `delivered`、`messageId` 与目标事实 | 可确认持久入箱，不足以显示通知、通信 ACK 或 agent 已处理；议题业务处理回执由模块保存 |
| mailbox 文件保存正文，SQLite 保存索引；通知泵处理 busy/offline，`sent` 只表示通知发出 | 复用 mailbox/pump，不建立另一套 agent 唤醒机制；通知发出不展示成 agent 已处理 |
| `lane_ack` 是通信处理回执，不带议题业务含义，且重复 ACK 会失败 | 保留旧契约；议题处理回执独立，不能用 ACK 自动结束议题 |
| `schema.ts` 的 `assertSharedSchema` 比较全库对象结构 | 使用已确认的独立议题库，保留 core 的严格校验，不为模块表放宽它 |
| 工具定义与 Zod schema 已共享，但各入口仍以固定的五个通信工具名判断 | 增加小型宿主工具分发层，保留原通信 `ToolService`，不向其 switch 塞议题业务 |
| 后台 HTTP 已独立为 `DashboardHttp` | 为议题提供相邻 HTTP 处理器，复用 HTTP/同源校验能力，不把业务写进原看板处理器 |

通用投递抽取已在本地提交 `0e15256`、`356028c` 完成，具体实现与验证见[投递底座计划](../plans/2026-10-17-tell-user-delivery.md)；后台 HTTP 整理也已本地完成。以上不代表在用 Router 已部署这些改动，更不代表议题功能已经实现；本轮没有查询或修改生产数据库。

## 3. 存储选择

| 方案 | 收益与成本 | 处置 |
|---|---|---|
| 一个 SQLite 文件、各自分表 | 可共用事务，但当前全库 schema 校验需改造；core 与模块迁移、回退必须协调。mailbox 文件仍不在 SQL 事务里 | 可行，暂不选 |
| 同进程、两个 SQLite 文件 | 模块独立建表迁移，保留 core 的严格 schema 校验；跨库交接使用持久待投递记录与稳定键重试 | 用户已确认，包括已说明的跨库约束代价 |
| 独立议题服务或通用插件运行平台 | 增加部署、通信和管理机制；当前流程不需要 | 不纳入 |

默认路径拟定为 `dataRoot/modules/issues/issues.sqlite`，由应用入口传给模块，不新增用户配置项。core 继续使用现有 `router.sqlite`；模块不导入 core 的数据库打开函数或迁移器。

独立文件是此实现的选择，不改变“至少按模块分表”的约束，也不把两个库变成架构必需条件。业务服务通过议题存储接口操作数据，未来更换存储适配不改变 UI 或 agent 工具规则。

### 跨库关联不是跨库外键

SQLite 不支持跨数据库 schema 的外键，`ATTACH` 也不解除这个限制；它可以让一个连接查询多个数据库，但不能把 `issues.sqlite` 中的字段变成引用 `router.sqlite` 表的强制外键。依据：[SQLite 外键限制](https://www.sqlite.org/foreignkeys.html#fk_unsupported)、[ATTACH DATABASE](https://www.sqlite.org/lang_attach.html)。

议题库内部可以建立真实外键，例如讨论条目引用本库议题。跨库的 `owner_lane_id` 则是逻辑引用：发布时由 core 解析并确认当前调用方所属 lane；投递时再按稳定 ID 检查目标存在及在役状态，不能只复用地址。core 当前只归档 lane，保留其原 ID 和记录，因此正常归档不会令历史身份消失。归档状态不等于外键断裂，也不等于仍可继续投递。

应用校验不等于数据库强制约束，不能阻止外部 SQL 绕过业务规则。单独替换/恢复其中一个库也可能造成引用缺失或状态不一致：此时保留历史、明确显示引用不可用并拒绝错误投递，不自动挂到同名 lane。两个库的恢复边界必须成对考虑，跨库步骤依靠持久交接而非原子事务。

如果要求插件引用 core 必须由数据库强制执行，应该改选同库分表，并明确单向外键和模块 schema 契约；不通过触发器或复制一份 lane 主表伪装跨库外键。插件化本身不要求分库。

模块库无法打开或结构不支持时，不覆盖、不重建为空库；通信 core 可继续运行，已装配的议题入口明确返回 `ISSUES_UNAVAILABLE`。不装配模块时不创建议题库或定时任务。备份与恢复须包含议题库及 WAL 的一致快照，不能只复制 core 文件就宣称保存了议题历史。

## 4. 模块边界与装配

拟定结构：

```text
src/router/                         通信 core，保留既有职责
src/tools/                          原通信工具服务与定义
src/application/tool-catalog.ts     宿主的工具集合、查找与分发
src/application/builtin-tools.ts    本独立产品的显式工具组合
src/modules/issues/
  service.ts                       议题业务服务
  types.ts                         业务类型与对外结果
  ports.ts                         存储、lane 身份与通信依赖
  store.ts / schema.ts              本模块 SQLite 表与迁移
  delivery.ts                      本模块持久交接与处理回执
  tools.ts / tool-schema.ts         本模块工具及参数定义
  http.ts                          议题 HTTP 适配，不依赖 HTML
  cli.ts                           同一套工具操作的 CLI 适配
src/ui/issues/                     展示和输入，不导入业务存储
src/process/main.ts                连接上述部件，负责进程生命周期
```

`IssueService` 依赖小型接口，不直接持有 `RouterCore`、`RouterStateStore`、`LocalRouterServer` 或前端对象。宿主提供通信接口的实现。core 不反向 import 议题模块。

工具目录只负责组合工具定义、检查重名、查找和分发。议题与原通信工具各自处理自身校验和业务。MCP 与动态工具的 JSON Schema 从各自的同一份定义生成；不能另外手写一套。原五个通信工具名称、参数、身份来源及行为保持兼容。

模块定义是显式、无副作用的贡献项；应用入口决定装配哪些贡献。MCP 子进程使用同一产品组合中的纯工具定义，不实例化数据库或业务服务。它的调用仍发给 Router 执行。不增加插件扫描、配置发现、依赖解析、运行时启停或通用事件总线。

## 5. 复用的通信接口与尚需补齐的身份端口

通用宿主入箱已经从旧 `tell` 抽出，不再列为看板的待实现任务。`UserMessageDelivery.deliverUserMessage` 接收 `target`、`source`、`body` 和 `requestKey`；议题适配器固定使用 `target: { laneId: ownerLaneId }`，来源由宿主确定，正文由模块组织。它返回 `delivered`、`messageId` 以及目标的稳定 ID、地址和当前状态。`delivered: true` 只表示已有持久 mailbox 邮件，不表示 agent 读过或处理过。

旧 `lane-router-lane tell`、`/lanes/tell` 通过 `TellAdapter` 保留输入限制、模板及返回契约。看板不把任意正文塞进旧主题字段，也不为自身新增公开的通用发送工具或网络路由。

| 能力 | 当前状态及本功能所需工作 | 必须遵守的边界 |
|---|---|---|
| 解析调用方 | core 已有 backend 身份解析及私有 `requireCallerBinding`；需提供窄的进程内身份端口 | 返回稳定 lane ID、binding ID、generation；模型不能在工具参数中声明身份，业务写入仍需确认 binding 有效 |
| 按稳定 ID 查询 lane | 存储已有 `laneById`；需由 core 的窄查询端口封装，模块不直接持有其存储 | 返回原 lane 的在役/归档、绑定与可达事实；地址复用不能重定向旧投递，目录中的地址列表不能代替稳定 ID |
| 宿主应用消息入箱 | `UserMessageDelivery` 已实现，直接复用 | 只接受可信宿主适配器确定的用户来源；议题每次提交以持久投递 ID 生成同一请求键 |
| 重试取得原入箱结果 | 已有同键重试，包括 ACK 与归档后重试 | 返回原邮件而不另发一封；重试可能推动待处理通知，因此不能当纯状态轮询使用 |

这些是进程内接口，不把任意发送方或任意用户输入入口公开给 agent 工具、DSH 或 Native Host。议题编号和业务状态只在模块生成的正文里出现，core 不解析它们。第一版不新增单独的入箱状态查询端口，不展示未取得证据的通知或通信 ACK 状态；准确状态由模块已保存记录、入箱结果及 agent 业务回执共同组成。

现有通用投递保证：成功写成的 mailbox 文件绑定请求键，同键同目标、来源与正文返回同一邮件，同键异内容报冲突；首次目标不存在或已归档、且未写文件的拒绝不保留请求键。文件成功但索引未写入时可以恢复同一文件；议题交接始终复用原请求键和内容，不把重试改成新的业务提交。

通用邮件已保留稳定目标 lane ID，孤立文件恢复及归档后重试不会把它交给复用该地址的新 lane。旧格式保持可读，旧 `send` 和 `ack` 对外契约未改。看板实现继续对这些行为做集成回归，不在 core 增加议题字段或重复建立恢复机制。

## 6. 议题数据与状态

下列为模块自有表的职责草案，字段与索引在实施计划中落实：

| 表 | 关键内容与约束 |
|---|---|
| `issue_thread` | 议题 ID、`owner_lane_id`、标题、open/closed、创建与结束时间、单用户已读序号；lane ID 是外部身份引用，不跨库建外键 |
| `issue_entry` | 不可变的正文、议题内递增序号、作者类别、来源、关联问题和条目、时间、实际记录者 binding；`(issue_id, seq)` 唯一 |
| `issue_question` | 提问条目、询问对象、等待用户/等待 lane/已回答/无需回答、关联答复；问题与条目必须同属议题 |
| `issue_delivery` | 看板回复的投递 ID、条目 ID、固定目标 lane ID、core 消息 ID、重试信息与 agent 处理回执；一个回复只有一个交接任务 |
| `issue_operation` | 调用方范围内的操作键、操作类型、请求摘要和结果；同键同内容返回原结果，同键异内容报冲突 |
| `issue_schema_version` | 本模块迁移版本，不改 core 的 `user_version` |

正文以 `issue_entry` 为业务权威；mailbox 中是不可变的传输副本，不支持两边分别编辑。状态变更留下相关条目/原因；不用删除正文表示撤回等待。第一版不增加多用户账户、编辑消息、附件或全文搜索。

议题 open/closed、问题等待状态、用户已读位置、消息交接/处理状态分别记录，不能压成一个枚举互相覆盖：

- 用户在看板回复后，该问题转为等待 lane；这不等于语义上已经答清楚，也不结束议题。
- 用户只是要求解释时，lane 补充解释后可继续等待用户作答；不能把所有用户回复自动当成最终决定。
- agent 标记已回答需关联具体答复；标记无需回答需保留原因。
- 待我处理包含仍等待用户的问题和未读的 lane 答复；列表结果附各自原因，不只给一个布尔值。
- 打开列表不标记已读；详情只提交实际展示到的序号，后端单调推进已读位置，不把刚到而未展示的答复一起读掉。

回复状态只展示有记录的事实：“已保存，待入箱”“已入 lane 收件箱，处理未确认”“agent 已确认处理”；交接错误或目标不可用另显示原因。lane 当前在线/离线可作为附加事实，但不推断正在执行。已确认处理也不等于问题已回答或议题已结束。

## 7. 工具、HTTP 与兼容入口

### 7.1 Agent 工具

| 拟定工具 | 操作范围 |
|---|---|
| `lane_issue_publish` | 创建本 lane 的议题并发布第一份内容，类别只能为用户问题的答复或主动向用户提问；答复类必须同时记录原问题 |
| `lane_issue_read` | 列出本 lane 的议题，或按 ID 读取分页历史、待回答问题与尚未处理的用户回复，供同 lane 新会话接续 |
| `lane_issue_append` | 向本 lane 的未结束议题追加答复、解释或提问；支持记录已在 TUI 发生的相关用户输入，不重复投递回当前 lane |
| `lane_issue_update` | 关联答复、撤销某问题的等待、记录指定用户回复已处理；不得自行关闭整个议题 |

修改操作使用业务操作键，不能只靠 RPC 连接内的 call ID 去重。工具参数不含 owner lane、backend、generation、伪造用户身份或一般性的 `confirmed` 字段。schema 只定义格式，状态规则仍由服务统一执行。

TUI 用户输入是 agent 对实际对话的记录，来源明确标成 `agent_reported_tui_user`，记录者身份仍由适配器提供。它不冒充网页直接提交的用户记录。引用文件或资源里的文字不能视为用户指令；后台也不宣称能独立核验 agent 没有完整上报的 TUI。

如果用户明确在 TUI 结束议题，草案采用专门的“记录 TUI 用户结束”操作，附原话并保留来源；它不是 agent 自行结束的通用操作，不能在普通状态更新中隐式关闭。用户确认了结束的产品边界，具体工具操作仍属本草案设计。

### 7.2 看板 HTTP

接口拟放在 `/issues/api`，由议题 HTTP 适配调用同一服务：

- 读取议题列表和详情，返回后端计算的待处理原因、历史游标和准确投递事实。
- 提交已有议题的回复，返回保存后的条目 ID、序号与交接状态。
- 标记已展示内容的已读位置。
- 明确结束议题。

不提供网页创建新议题或任意选择目标 lane 的写入口。请求中的 issue ID 经服务解析其归属；不能让用户另传 target 改写投递对象。

复用现有 loopback、同源、JSON、action header 和进程 action token 约定。通用的 HTTP 校验由宿主辅助层提供，网页不调用机器 `/rpc` 来冒充 agent。正文按不可信文本展示，不允许原样 HTML 执行。服务接口不依赖 HTTP token，其他产品由自身适配器提供相应调用方边界。

### 7.3 不同工具环境的接入

| 环境 | 方案与证据边界 |
|---|---|
| 新建 Codex 会话 | 通过已有动态工具适配注入组合后的定义；真实调用仍需后续验收 |
| 已有 Codex 会话 | 不假设恢复就能增加动态工具；提供 `lane-router-lane issue` CLI 分组，调用相同模块操作，身份从宿主环境取得，不能由模型填写 lane 归属 |
| Claude / ZCode 的常规 lane | 扩展既有 stdio MCP 工具定义与 Router 分发；已运行 MCP 进程的工具刷新/重连需验证，不宣称热更新已支持 |
| DSH / Native Host 等受限宿主 | 用户已确认不纳入首版 Host 协议改造；保留其现有工具白名单与身份约束，不因新目录组合就自动开放议题能力，不能冒充已经覆盖 |
| 嵌入其他产品 | 使用议题业务服务及必要适配；不必引入本看板。第一版不承诺另发 SDK 包 |

CLI 分组是旧 Codex lane 的兼容工具入口，不新增一套业务、数据库或通信协议，不触发 TUI 重开/轮换。格式校验及业务操作定义复用模块工具；只在能解析当前会话并确认有效绑定时执行，否则明确拒绝，不能退回让模型任选身份。常规 MCP 接入也不改成所有用户必须走 CLI。

本机只读证据：`codex-cli 0.163.0` 导出的 `ThreadResumeParams` 没有 `dynamicTools`，现有桥接也只装饰 `thread/start`；当前 shell 具有匹配本 lane 的 `CODEX_THREAD_ID`。这证明设计有兼容入口的身份来源，不证明新 CLI 已实现或所有环境都支持。官方文档说明动态工具会随会话保存/恢复，并提供 MCP 配置刷新，但不能据此承诺本机旧动态工具可任意替换。参见 [OpenAI App Server 文档](https://learn.chatgpt.com/docs/app-server#dynamic-tool-calls-experimental)。

## 8. 保存、交接与结束边界

### 8.1 用户回复

1. HTTP 适配校验本地用户入口，服务检查议题和目标 lane、关联问题及操作键。
2. 单次议题库事务保存用户正文、问题等待状态、唯一投递任务与操作结果；事务成功后即可准确返回“已保存，待处理”。数据库失败不确认提交成功。
3. 模块交接器通过已有 `UserMessageDelivery` 提交同一投递键、固定 `owner_lane_id` 和来源。正文携带议题/条目 ID、必要上下文及查询方式，明确这是用户回复，可以在原授权内继续，不要求回 TUI 复述。
4. core 入箱成功后记录其消息 ID。后续唤醒和 busy/offline 保留由现有通知泵负责，不另建一套通知机制。
5. agent 读取完整回复和议题当前状态，处理后保存关联答复/业务处理回执，最后走普通 `lane_ack`。处理回执不能由通知发出或 ACK 自动推断。

模块交接器只重试尚未成功入箱的持久记录，启动时恢复，运行时有上限退避；它不是独立后台进程。交接失败不丢正文，浏览器关闭不影响后续尝试。core 已入箱但模块尚未记下结果时，以同键重试取得原结果；两库之间不假装有原子事务。

如果邮件已入箱但没有议题处理回执，即使 agent 实际已做通信 ACK，页面也仍显示“已入 lane 收件箱，处理未确认”。本版没有 ACK 查询证据，不显示“通信已确认”，也不因缺少业务回执再次发邮件或自动执行用户任务。正常操作顺序通过工具说明和验收约束；无法保证任意 agent 的业务副作用恰好一次。

### 8.2 失败与竞态

| 情况 | 应有结果 |
|---|---|
| 回复提交后 HTTP 响应丢失 | 使用同一操作键重试/查询，返回原条目；不能因为不确定就要求正常重发正文 |
| 存储成功，交接前进程退出 | 从持久交接记录恢复；不依赖页面 |
| core 文件已写、索引或模块回执未写 | 校验稳定键、邮件 ID、正文与目标身份后接管，不生成第二封 |
| lane 忙碌或离线 | 保留已保存回复和 pending 邮件，显示事实，不启动 TUI |
| lane generation 改变 | 同一 lane ID 的当前会话可读取历史并继续，旧 binding 不得继续写 |
| lane 已归档或地址被其他 lane 复用 | 不重定向。新回复明确拒绝；此前保存的未完成交接保留并显示目标不可处理 |
| 操作键重复但内容不同 | 冲突，不覆盖原内容 |
| 新答复到达与用户标已读并发 | 已读仅推进到用户实际展示序号，新内容保持未读 |

### 8.3 “在路上”不是新的产品能力

它只指普通并发：用户点结束时，agent 可能还在生成答复；或答复提交请求与结束请求恰好交错。没有必要把它做成“结束后继续接收讨论”的功能。

按用户已确认的边界，以服务事务提交顺序决定：答复先提交，保留后再结束；结束先提交，后来的新追加返回 `ISSUE_CLOSED`，不能重开、变成新的待处理或静默新建议题。同键重试已经成功的旧操作仍返回原结果，不因结束把成功操作改报失败。

已经保存的用户输入不因结束而被撤销；结束不等于取消正在执行的任务。已有投递的处理回执属于事实补记，可在结束后记录，但不能借此追加讨论或重开。回执补记和幂等结果属于本草案的工程处理，不是新的结束后讨论入口。

## 9. 验证与实施顺序

仅描述设计后的实施顺序，不代表现在开始执行：

1. 复用已实现的 `UserMessageDelivery` 与后台 HTTP 边界；补齐窄的身份/稳定 lane 查询端口，实现模块业务、存储与工具组合边界；以无真实模型的隔离 fixture 验证，不重做已完成的投递抽取。
2. 接上常规工具、旧会话兼容 CLI 和 HTTP，确认同一调用经过不同适配仍执行同一规则。
3. 用户看过样稿后实现 UI，最后做实际后端接入的端到端验收。构建在隔离工作树，部署交外部对话，不从本 lane 重启在用 Router。

关键验收：

- 不装配议题模块时，旧通信工具和 core schema 完全可用，不创建模块文件。
- 工具定义/schema 在动态工具、MCP 和兼容 CLI 中一致；身份参数注入被拒绝，旧 binding 写入被拒绝。
- 同 lane 轮换可接续；归档同名新 lane 不能读取/接收旧议题的新输入。
- 只发布允许的两类；TUI 同步不回声投递；用户从看板回复无需回 TUI 重复。
- 澄清不等于最终回答、单轮答复不结束议题、读过问题仍可待回答。
- 关闭浏览器、断开 HTTP、busy/offline、关键提交点重启、重复调用与异正文冲突均有 fixture。
- 验证 mailbox 孤立文件、索引恢复及归档后重试，不把“有操作键”当成完整可靠性证据。
- 独立消费议题服务时不加载 UI/HTTP；测试依赖图禁止 core import 模块和 UI import 存储。
- 真实旧 Codex lane 的 CLI 以及现有 MCP lane 更新后可用性单独实测；schema 存在不冒充运行通过。
