# 问答页已读：窗口有焦点、条目末尾进入过视野才算读过 —— 需求与设计

**状态：** 需求与设计合一稿，2026-10-19 由 `lane-router/inbox` 起草。用户同意按推荐改（评估议题 `ca0bc5e7` 条目 #4），并确认长条目「末尾进入视野」才算读过（议题 `aeb7615e`）。用户说过「出了方案直接推进到做完」（议题 `e5f33070`），所以稿子写完直接交给 `lane-router/impl`。第五节是验收标准。Vikunja #343。

> 2026-10-19 修订：impl 实施时实测发现，「宽屏以历史区为 root」在矮窗口下会把窗口外的条目也算成见过，于是改为不指定 root（见第二、三、五、六节）。用户确认的口径「窗口有焦点、条目末尾进入视野才算读过」没有变。

## 一、问题与结论

现在每次成功读取详情后，页面都会调用 `markRenderedRead`（`src/ui/issues/index.html:367`），把已加载的内容全部标为已读（`:511-524`），检查条件只有一条：标签页不是隐藏状态。窗口有没有焦点、内容有没有滚到眼前，都不看。

所以，问答页开在副屏、用户人在 TUI 里干活时，新答复 5 秒内就会被标成已读，「未读答复」标记根本出现不了。改成框内滚动以后，历史区之外的条目也会在渲染时被一起标读。

结论：已读位置只推进到「窗口有焦点时，末尾进入过可视区的条目」。

## 二、选型

| 选择 | 采用 | 理由 |
|---|---|---|
| 看条目的**末尾**是否进入过可视区 | 是（用户确认） | 比屏幕还高的长答复，只露出开头不算读过 |
| 窗口要有焦点（`document.hasFocus()`），且标签页可见 | 是 | 副屏开着、人在别的窗口时不算在读 |
| 已读位置 = 末尾见过的条目里最大的 `seq` | 是 | 服务端的 `readSeq` 本来就是只增不减的水位线；用户跳着往下看，就当作跳过的部分也看过了。不另存逐条已读 |
| 可视区 = 浏览器视口，再被途经的滚动容器（宽屏下就是历史区）裁剪；`IntersectionObserver` 不指定 root | 是 | 这正好是用户眼睛能看到的部分。2026-10-19 impl 实测（Edge 155）：窗口矮于约 520px 时，页面本身会整体滚动，历史区的下半截落到窗口外。这时如果以历史区为 root，会把窗口外的条目也算成见过（1280×440 时会发出 `throughSeq` 8，而第 8 条的末尾在 y=488，窗口只到 440）；不指定 root 则不会。正常尺寸下两种写法结果相同。这样也省掉了按断点切换 root 的代码 |
| 获得焦点时，对当前可视区里的条目补一次判断 | 是 | 用户切回窗口时，眼前的内容就算读过，不用再滚一下 |
| 浏览器没有 `IntersectionObserver` 时不推进已读，不退回「渲染即已读」 | 是 | 退回旧行为就等于没修；目标浏览器都支持它 |
| 后端不改 | 是 | `POST …/read` 收 `throughSeq`，服务端取最大值（`service.ts:182-192`），已经够用 |

## 三、设计

- 页面给每个条目的末尾放一个观察点（实现方式由 impl 定，例如条目末尾一个零高度元素），用 `IntersectionObserver` 观察，不指定 root：可视范围就是视口，再被途经的滚动容器裁剪（宽屏下就是历史区）。宽屏、窄屏用同一个观察器。观察点进入可视区时，记下这个条目「末尾见过」。
- 只有在「标签页可见并且 `document.hasFocus()`」时进入可视区，才算见过。窗口失焦期间进入可视区的条目，在窗口获得焦点（`focus` 事件）时重新判断：仍在可视区里的算见过。
- 有新的「见过」时，计算 `throughSeq = 见过的最大 seq`；大于 `max(readAck, thread.readSeq)` 时发送已读。沿用现有的「每个 `throughSeq` 一个 `operationKey`」和失败重试机制（`:515-523`）。
- 去掉「每次读完详情就标读」这一调用。轮询带来的新条目只有在满足上面的条件后才标读。
- 打开议题时的定位和分隔线，仍然用本次选中后第一次取到的 `readSeq`（滚动稿规则 1）。行为不变，因为标读只会更晚发生。
- 切换议题时，前一个议题的观察全部停掉；新议题的条目重新观察。

不改：后端、HTTP、列表上「未读答复」的口径（`store.ts:59`）。

## 五、验收标准

第 1–5 条在真实浏览器里测（沿用滚动稿的 Edge/Playwright 做法）；第 6 条用 happy-dom；第 7 条是真机。

1. 宽屏，窗口有焦点：打开一个末尾有 5 条未读、历史区只放得下其中前 2 条的议题，发出的 `throughSeq` 等于末尾可见的最大 `seq`，后端 `readSeq` 停在这里，列表上仍显示「未读答复」。滚到底以后，`readSeq` 等于最后一条的 `seq`，「未读答复」消失。
2. 一条比历史区还高的答复，只露出开头时不推进到它；滚到它的末尾后才推进。
3. 窗口没有焦点（测试里替换 `document.hasFocus` 并派发 `blur`）：轮询带来一条落在可视区里的新答复，不发已读。派发 `focus` 后，发已读，推进到它。
4. 标签页隐藏时不发已读（现状保留）。
5. 窄屏（375×800）下用视口判断：只有末尾滚进视口的条目才推进。宽屏矮窗口（1280×440，页面本身在滚动）下：末尾在历史区内、但落在窗口外的条目，不推进。
6. happy-dom：没有 `IntersectionObserver` 时从不发已读；已读失败时的重试与同键重放行为，与现有测试一致。
7. 真机：在跑的 Router 读到新页面后，把问答页放在另一个窗口不聚焦，让 lane 发一条答复，确认「未读答复」出现并保持；切回去滚到底后消失。记入 `docs/manual-tests.md`。

现有测试不删；断言所测的行为确实变了的（「渲染即已读」），可以改，但要在交付说明里逐条列出改了哪条、为什么改。`npm test`、`npm run typecheck` 全部通过。

## 六、验证方法与变异检验

- 跑法：`npm test`、`npm run typecheck`。主检出不 build；测试一律用临时数据目录，不碰共享 Router。
- 变异检验（每次改坏一处，看对应的测试有没有变红，看完改回）：
  - 恢复「读完详情就标读」 → 1、3 变红
  - 用条目开头代替末尾 → 2 变红
  - 不判断焦点 → 3 变红
  - 获得焦点时不补判断 → 3 变红
  - 宽屏以历史区为 root → 5 变红（矮窗口那一条）
  - 没有 `IntersectionObserver` 时退回渲染即已读 → 6 变红

## 七、边界

- 已读仍是整条议题的一个水位线，不记录逐条已读。
- 议题超过 100 条、最新内容还没加载时，已读只能推进到已加载的部分（分页方向另见 Vikunja #345）。
- 只是页面改动；在跑的 Router 读到新页面的时机归用户。
