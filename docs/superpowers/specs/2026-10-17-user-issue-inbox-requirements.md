# 用户议题收件箱（问题看板）需求确认稿

状态：需求汇总已获用户认可，整体架构设计于 2026-10-18 获用户确认，当前进入实施计划确认阶段；本文不包含本功能的实现或部署授权。

## 目的

用户同时与多条 lane 工作，离开 TUI 后，lane 给用户的答复以及主动向用户提出的问题可能被后续消息淹没。后台需要一个集中入口，让用户找回这些问答，并直接围绕原问题继续讨论，不必复述问题、手工对应答案或回 TUI 重复指令。

本文称这个入口为“看板”，称其中一个问题及其相关多轮讨论为“议题”。议题的结束与某一轮提问是否已经得到回答，是两回事。

## 已确认需求

### R1：收录范围

只收两类内容：

1. 用户在 TUI 向 lane 提问后，lane 给用户的答复。
2. lane 主动向用户提出、需要用户回答或决定的问题。

普通进度广播、工具执行过程、lane 间通信不进入。用户主动询问进展后得到的答复仍属于第一类，不能因正文包含进度而排除。

lane 能明确提交应进入看板的内容。具体工具和发布方式留到技术设计，不通过需求稿规定协议或接口。

### R2：议题从 TUI 发起

新议题从 TUI 对话侧产生并发布到看板。看板第一版不提供选择 lane 后主动新建议题的入口。

看板允许在已有议题中继续回复、追问、要求解释和补充条件；这些能力不因没有“新建议题”入口而受限。

### R3：按问题组织，支持异步多轮

用户在议题内回复，回复直接对应原问题，不需要再复制问题或手动声明“这段答案对应哪个问题”。同一问题的相关问答保留在同一议题中，方便继续讨论。

第一版支持异步多轮，不采用“提问一次、回答一次就完成”的限制。用户可以先弄清问题，再给出决定。

### R4：看板回复是有效用户输入

用户在看板回复后，lane 在原任务授权范围内直接继续处理。不能只把回复记为一条便笺，也不能要求用户再回 TUI 复述或重复确认同一答复。

这不扩大原任务授权范围，也不取消其他本来就适用的安全或授权边界。

### R5：TUI 与看板之间同步相关讨论

用户可以从看板切回 TUI 回答已有问题。agent 负责把相关答案及后续回应同步回原议题，不要求用户手动搬运或配对。

只同步议题相关的讨论，不同步整份 TUI 对话、工具轨迹或普通广播。

### R6：区分已回答与议题结束

只有用户明确结束整个议题。阅读、发送回复、lane 得到答案或通信确认，都不自动结束议题。

agent 得到某个问题的答案后，可以把该轮问题标记为已答复，取消“等用户回答”，并继续工作。它不能因此删除问题或关闭整段讨论。

如果问题已经失效，或 lane 自行解决、不再需要用户回答，agent 可以标记“无需回答”，移出待处理，但保留记录，不自动结束整个议题。

用户结束议题后，agent 不自动重开它。后续有新的相关问题时，从 TUI 对话侧新开议题，而不是恢复旧议题的等待状态。

### R7：默认突出需要用户处理的内容

“待我处理”主要突出：

- lane 仍在等待用户回答的问题。
- lane 给出了新答复、用户还没有看过的内容。

需要用户回答的问题即使已经读过，仍然是待回答，不能因已读而消失。用户已经回复、正在等 lane 继续的议题仍保留可查，但不混在“待我处理”中，也不自动结束。

### R8：忙碌、离线与投递状态

用户回复先可靠保存。lane 忙碌时排队，待其可处理时继续；lane 离线时保留，待其恢复后处理。

第一版不因为看板收到回复而自动重开 TUI。尚未处理的状态对用户可见，不能让用户以为 lane 已经处理，也不能要求用户为了正常排队或离线保留而重复发送。

### R9：历史保留，搜索不是第一版必做项

原问题、相关往返内容、答复与议题的对应关系，以及已结束的讨论保留可查。不采用只保存最新答复、丢弃前文的方式。

第一版不把专门的搜索功能列为必做项。简单历史浏览即可满足当前边界；后续可以补充按 lane、项目或关键词查找。保留信息与关联有利于以后补检索，但不把“已经保存”宣称为“已经具有搜索能力”。

### R10：辅助入口，不替代 TUI

TUI 继续承担新话题发起、lane 创建或启动以及直接沟通等既有用途。看板聚焦已发布议题的集中查看和讨论，不扩展成完整 TUI 镜像或全部工作控制台。

第一版不做桌面、声音等主动通知；用户进入后台查看待处理内容。

### R11：功能与 UI 分层，业务能力可供其他产品使用

Lane Router 不只独立运行，也会向其他产品提供底层 lane 通信能力。本功能的业务能力不能依赖看板页面、浏览器状态或特定前端框架才能工作。

UI 负责展示后端结果和采集用户输入。议题与消息的权威记录、状态变更规则、持久化、排队和投递由后端业务能力负责；网页关闭、更换 UI 或其他产品不使用本项目看板时，这些能力仍能使用。

用户提交回复必须由后端可靠保存后，才可向用户确认已提交或已保存。不能把“先存前端、之后依赖页面继续运行再同步”作为成功提交的实现。尚未保存到后端时，UI 必须准确反映未提交或失败，而不是制造成功状态。

输入框中的临时编辑内容不等于已提交的消息，不能作为可靠保存或投递的依据。已提交回复的继续投递不应依赖用户保持该页面打开。

不同 UI 或产品接入应使用同一套后端业务规则，不能各自实现一套议题生命周期或投递语义。具体采用库调用、服务接口还是其他适配形式，后续再讨论；这条约束不直接规定新增 SDK、协议或部署形态。

### R12：现在明确 core/plugin 边界，为后续插件形态保留拆分条件

用户要求设计插件雏形：当前可以采用内置的独立功能模块，但必须明确通信 `core` 与议题管理 `plugin` 的职责和依赖边界，不能只把混杂实现换成不同目录。

通信 core 不反向依赖议题模块，不承担该模块的专有议题状态或规则。议题管理建立在通信能力之上，按自身职责组织业务、数据与接入适配；具体接口和装配方式在后续设计中确定。

后续转成插件时，应能围绕模块装配与交付边界进行调整，不以大规模重写通信核心和搬迁散落业务为前提。“为以后方便拆分”需要在本轮设计中体现为明确的依赖方向与职责归属，而不是仅留一条未来重构待办。

当前不直接要求独立安装、动态发现/加载、运行时启停、热更新、插件市场或完整的插件框架。只有后续具体需求确实需要时，再单独讨论这些能力。

## 第一版之外

- 普通进度流、工具日志和全量 TUI 对话镜像。
- 从看板主动新建议题。
- 因收到回复而自动启动或恢复 TUI。
- 系统级主动提醒和专门的高级搜索。
- 外部资源接入、围绕资源的新产品能力、图展示与交互，以及通用资源平台。

外部资源讨论是用户的后续方向，可能复用本功能的某些能力；这只是后续设计背景，不授权第一版预建通用底座。图展示库选型由独立 lane 调研，不改变本稿需求。

## 验收场景

| 场景 | 用户应看到的结果 |
|---|---|
| 用户在 TUI 提问后离开，lane 后来给出答复 | 回到后台能找到对应问题及答复，不必翻后续消息定位 |
| lane 主动问用户，用户暂时没有回复 | 问题进入待回答并保留；读过不等于答过 |
| 用户不理解问题，先要求解释 | 同一议题支持继续问答，不在第一轮回复后自动结束 |
| 用户在看板给出决定 | lane 在原授权范围内继续工作，不要求用户去 TUI 重复 |
| 用户改在 TUI 回答 | agent 把相关问答同步回原议题，取消该轮待回答状态 |
| lane 后来发现无需用户回答 | 可撤销等待，但问题与处理记录保留，整个议题不自动结束 |
| 用户明确结束后又有新问题 | 新问题成为新议题，旧议题不被 agent 自动重开 |
| 用户回复时 lane 忙碌或离线 | 回复已保存且待处理状态可见，之后继续处理，无需用户正常重发 |
| 用户提交回复后关闭看板页面 | 后端仍保留已提交的回复，并能在 lane 可用时继续处理，不依赖浏览器代为保存或投递 |
| 回复尚未保存到后端 | UI 不显示提交成功，前端暂存不能冒充后端可靠保存 |
| 其他产品不用本项目看板而接入相关能力 | 不需要复制前端业务逻辑，仍使用同一套后端规则处理消息与议题 |

## 已确认的架构选择

### A1：第一版同进程运行，由应用入口装配

通信 core 与议题模块先运行在同一个 Router 进程内，由应用入口选择并连接所需模块。代码依赖、业务规则和数据归属仍保持分离，不因同进程而合并职责。

UI 通过后端能力展示和提交内容，不承担业务权威。只需要通信能力的产品可以不装配议题模块；第一版不另建独立的议题服务，也不引入新的服务部署流程。

这是第一版的运行与装配选择，不代表动态插件加载、独立进程隔离或其他插件框架能力已经纳入范围。

### A2：业务数据按模块分表，通信状态与议题状态分开

通信 core 管理 lane 身份与绑定、消息投递、排队和通信回执。议题模块管理问题与相关多轮讨论、已读位置、等待谁回答、无需回答以及用户结束议题等业务状态。消息已投递不等于 agent 已处理，也不自动意味着问题已回答或议题已结束。

两者可以共用一个数据库，但必须各自拥有业务表及其读写规则，不能混用同一张业务表承载两套职责，也不能把议题专用字段塞入 core 表。实际表数不限定为两张，具体表结构留到数据设计。

议题模块通过明确的通信接口使用 core，不直接操作 core 的内部表；core 不读取议题模块的表来决定通信行为。UI 只展示后端结果并采集输入，不自行维护这些权威状态。

### A3：统一业务服务，工具与 HTTP 分别适配

议题模块提供统一的业务服务，负责业务校验、状态变更和持久化，并通过 core 使用通信能力。lane 使用的工具和看板使用的 HTTP 接口分别适配该服务，不各自实现一套议题规则。其他产品不使用本项目看板时，仍可使用同一业务服务。

模块提供自己的服务、工具定义和接口适配，由应用入口将其接入 Router。通信 core 不识别具体插件，议题命令不进入现有通信工具的业务分支。第一版采用显式装配，不做动态扫描或加载。

### A4：议题属于 lane，不属于某一代会话

议题绑定 lane 的稳定身份。会话恢复或同一 lane 的代际轮换不改变议题归属；新会话处理已有议题时可以取得相关历史。lane 地址被归档后重新使用，不代表原 lane 的身份延续，旧议题不能因此转交给另一个 lane。

### A5：结束后拒绝新的讨论追加，已保存的记录保留

用户认可按后端提交顺序处理结束与答复并发：先保存的记录保留，结束成功后拒绝新的讨论追加。不额外设计“迟到回复”接收功能，不自动重开或静默新建议题。

### A6：采用两个 SQLite 文件，跨库通过稳定 ID 与业务接口关联

用户在了解跨库不支持强外键、备份恢复需要协调等代价后，确认 core 与议题模块分别使用 SQLite 文件。两个文件是两个数据库，不代表两个服务进程。模块内部的关系使用本库外键；模块引用 core 的 lane ID 则通过稳定 ID 和业务接口校验，不能把它宣称为数据库强约束。同库分表仍是可行架构，但本功能不再沿该候选继续设计。

### A7：首版覆盖常规 TUI lane，不改造外部产品 Host 协议

用户确认首版覆盖 Codex、Claude、ZCode 等常规 TUI lane，不同时改造通过 Company 等其他产品接入的 DSH/Native Host 协议及其工具白名单。模块业务服务仍保持可供其他产品接入的边界，但不能据此宣称这些受限 Host 已支持本功能。

### A8：看板采用议题列表与详情分栏

用户看过两种样稿后选择“列表与详情”：列表用于在多个议题间切换，详情展示选中议题的相关讨论和回复入口。不采用议题卡片逐项展开作为主要布局。样稿的模拟发送和数据不代表后端功能已经实现，也不构成对所有演示交互细节的确认。
