# 通信治理层 设计稿（design only，本轮不动代码）

**状态：** 设计稿。来源：2026-08-31 dsh 评估 handoff 的决策 1 与工作项 4（见 [`2026-08-31-dsh-harness-evaluation.md`](2026-08-31-dsh-harness-evaluation.md)）。用户已批准**方向**，并明确本轮只出稿。

**本稿的结论先说：批准的四个机制里，只有两个有证据支撑，另外两个不该建。** 依据是本机 4637 封历史消息的实测，见第二节。

## 术语表

| 词 | 含义 |
|---|---|
| 治理 | Router 在写路径上做的机械约束，跟「靠 agent 自觉」相对 |
| 硬控制 / 建议性控制 | 前者是能力被拿走，后者是能绕过。这个区分决定本稿能承诺什么 |
| 背压 | 收件方积压到一定程度时，对发件方产生的反馈 |
| 发送调用 / 消息行 | 一次 `lane_send` 是一个调用；带 `cc` 时它产生 N 行 |

## 一、先把天花板说清楚：这一层只能是建议性的

治理层容易被读成「从此发不出去了」。**它做不到，而且做不到的原因不在实现质量。**

被治理的一方是坐在 shell 前的 agent。它能读写这台机器上的任何文件，包括策略文件、包括 Router 的数据库。任何「策略存在某处、Router 读它」的方案，被治理者都能改那个某处。

⇒ 这一层**只能是建议性控制**。真正的硬控制要求「一个独立的签名方 + 一个被治理方改不了的验证方」——本项目**没有**那个结构，本稿也不打算引入它。

**这不是缺陷，是定位。** 建议性控制防的是**意外**，不是**恶意**：

| 它防得住 | 它防不住 |
|---|---|
| 一条 lane 不知道对方已经堆了 37 封，又发了一封 | 一条 lane 决心绕过它 |
| 有人以为在正文里写「抄送 X」就抄送了 | 有人直接改策略文件 |
| 赶时间时跳过该做的检查 | — |

⚠️ **这句话必须写在稿子最前面**，因为下游最可能的误用是：建了这一层，然后**因为「有治理了」而放松别处的纪律**。它挡不住任何一个真想绕的人。

## 二、四个机制，逐个找证据

用户批准的是**方向**，不是「四个都建」。按本仓库既有的「扩张由证据触发」纪律（见 [`2026-08-12-prior-art-and-build-vs-adopt.md`](2026-08-12-prior-art-and-build-vs-adopt.md) 第五节），逐个问：**我们有没有它防的那个故障？**

测量对象：本机 `router.sqlite`，4637 封消息，2026-08-31 取数。

### ⚠️ 先纠正一个差点被我用错的数

第一遍查「单发件方单日发信量」，最高是 `mocap/ui` 在 2026-08-28 的 **374**。这个数看起来足以支撑「需要频率预算」。

**但它不是发送次数。** `cc` 会让一次调用产生 N 行，实测放大 **1.9–3.2 倍**：

| 发件方 | 日期 | 消息行 | 实际发送调用 | 放大 |
|---|---|---|---|---|
| `mocap/ui` | 08-28 | 374 | **125** | 2.99× |
| `mocap/render` | 08-28 | 281 | **89** | 3.16× |
| `mocap/design` | 08-28 | 201 | **69** | 2.91× |

⇒ 记下来当判例：**一个数要跟着它的机制一起走。** 差一步就用「374 封／天」去论证一个机制，而真实量级是它的三分之一。

### 2.1 未 ack 背压 —— ✅ 有强证据，建

扫全部 created / resolved 事件算「历史同时 pending 峰值」：

| lane | 峰值同时未处理 |
|---|---|
| `mocap/render` | **37** |
| `mocap/hub` | 21 |
| `mocap/ui` | 21 |
| `mocap/arch` | 8 |

最长 ack 时延 **63.8 小时**（`mocap/design` 收到 `mocap/render` 与 `mocap/ui` 的两封）。

⇒ **37 封同时压在一条 lane 上，是这套系统真实发生过的状态**，不是设想。这是四个机制里唯一有硬数字的。

### 2.2 强制收件人声明 —— ✅ 有证据，但缺口已被 `cc` 补掉大半，建**小的**那一半

证据是既有的：[`2026-08-20-lane-send-carbon-copy.md`](2026-08-20-lane-send-carbon-copy.md) §1.1 记录了「**一个从不存在的机制，被当成存在的**」——lane 在正文里写「(cc render)」，以为抄送了，而 Router 从不读正文。

`cc` 落地之后，**做得到**这件事了。剩下的缺口只有一个：**正文里写了而参数里没写时，仍然静默无事发生。**

### 2.3 频率预算 —— ❌ 无证据，且有反证，不建

峰值 125 次调用／天（`mocap/ui`，2026-08-28）。查这一天是什么日子：**mocap 的架构重构日**，多条 lane 并行推进。

⇒ 这个量**不是故障，是产出**。频率预算若当时在线，限的正是那天的工作。**没有任何一次记录在案的损害可以归因于发得太多。**

⚠️ 反过来说：真正的痛点是**收件方处理不过来**（2.1 的 37 封），不是发件方发得太快——**背压管的是前者，频率预算管的是后者，而我们只有前者的证据。**

### 2.4 路由白名单 —— ❌ 无证据，且有反证，不建

跨项目发送共 **24 对**，量最大的几对：

```
of_retarget_maya ↔ RetargetStudy : 61 / 58
RetargetStudy    →  mocap        : 26
motus_kit        ↔ mobu_motion_bridge : 26 / 25
mocap            ↔ lane-router  : 13 / 12
```

**逐对看下来没有一对是不该发生的**——它们正是这套系统存在的理由。本稿写作当天还发生了一次：`mocap/design` 跨项目问 `lane-router/design` 一个机制问题，解开了它那边卡住的迁移。

⇒ 一份要允许全部 24 对的白名单，**等于没有白名单**，却带来一份必须随拓扑变化维护的配置。**不建。**

### 小结

| 机制 | 证据 | 判定 |
|---|---|---|
| 未 ack 背压 | 峰值 37 封、最长 63.8 小时 | ✅ **建** |
| 强制收件人声明 | cc 稿 §1.1 已记录的真实误解 | ✅ **建小的那一半** |
| 频率预算 | 无。峰值那天是产出不是故障 | ❌ 不建 |
| 路由白名单 | 无，且 24 对跨项目全是有用的 | ❌ 不建 |

## 三、设计（只针对留下的两个）

### 3.1 背压：先告知，后拒绝，且更正永不拒

**触发点在 `send` 里**，收件人校验通过之后、写入之前。

三档，按收件方当前未 ack 封数与最老一封的时长：

| 档 | 行为 |
|---|---|
| **通过** | 照常写入 |
| **告知** | 照常写入，但返回值里带一句：目标当前有 N 封未处理、最老一封已 X 小时 |
| **拒绝** | 不写入，错误里说清 N、X，并给出下一步（让对方先 ack，或者改发给协调方） |

三条硬约束：

1. **`correction` 永不拒绝。** 更正的意思是「上一封说错了」——它恰恰是积压时最必须送达的一封。拒绝它会让一条错误信息留在对方的队列里，而纠正被挡在门外。
2. **拒绝必须给出路。** 照 cc 稿 §3.5 的先例（`RESTORE_LANE_OUTSIDE_PROJECT` 的消息里带可直接复制的命令）：一个不给出路的拒绝，只会让对方绕过去。
3. **`cc` 逐收件人判定。** 一次带 cc 的发送，可能对 A 通过、对 B 该拒。⚠️ 这跟 cc 稿 §3.1 的「全有或全无」**直接冲突**——那条要求任一收件人不合法就整次失败、一个字节都不写。

   ⇒ **本稿的裁定：背压不参与「全有或全无」。** 地址非法是**发件方写错了**，整次拒绝能让它改对；而背压是**收件方的状态**，跟这次发送的正确性无关。让 B 的积压挡住发给 A 的那封，是把别人的问题算到发件方头上。**实现时这条要单独有测试**，否则会被顺手做成整次失败。

**阈值本轮不定。** 决策 4 说得明白：先有观测数据再定阈值。上面那些历史数字（告知≈10、拒绝≈30 是它们暗示的位置）**是回头看算出来的，不是运行中观测到的**——看板上线后按真实分布定，届时写进实施稿。

### 3.2 收件人声明：只补那个静默的缺口

`cc` 已经让「抄送」这件事**做得到**。剩下的缺口是：正文里写了抄送、参数里没写，**什么都不会发生，也没有任何信号**。

**做法：发送时扫正文里形如 lane 地址的字符串，凡是没出现在收件人清单里的，在返回值里点名。**

- **只提示，不拒绝、不改路由。** 正文里提到一条 lane 有很多正当理由——引用、转述、说「这个问 X」。把提及当成投递意图去执行，是**替发件方做决定**。
- **判据要窄**：只认 `<project>/<lane>` 这个确切形状，且该地址在库里真实存在。宁可漏报，不要误报——一个经常误报的提示，几次之后就没人看了，那时它等于不存在。
- **不进正文、不进消息记录**，只在 `lane_send` 的返回值里。它是给发件方当场看的，不是给收件方的。

### 3.3 策略的修改权限：不能给 agent，而且要正视它挡不住什么

**这是本稿最要紧的一条设计题。**

背压的阈值是拓扑级配置。**若它可由对话工具修改，那么被治理的一方就能自己放宽治理**——这不是假想的滥用，而是最自然的行为：agent 撞上拒绝、看到有个工具能调阈值、调了它，然后继续。整个机制在第一次真正生效时就被解除了。

⇒ **三条，按 `lane_attach_current` 的先例（`tool-contract.ts` 的 `ATTACH_CONFIRMATION`）：**

1. **不新增任何修改策略的对话工具。** 工具数保持 5 个。
2. **改阈值走 shell**，跟退役同一条路（`lane-router-lane`）——agent 要改就得在对话里说出来，人看得见。
3. **不加「确认参数」。** cc 稿与退役稿都遵守这条：一个 `confirm: true` 参数是 agent 自己填的，它证明不了人同意过，只制造同意的外观。

⚠️ **而它挡不住什么，要连着写**（第一节的具体化）：agent 有 shell，能直接跑那条命令，也能直接改文件。这三条防的是**「顺手就把它关了」**，不是**「决心关掉它」**。价值在于**改动会留下人看得见的痕迹**——一条命令出现在对话里。

## 五、这份稿子会被什么推翻

- **看板上线后的真实分布跟历史回看不一致。** 那时阈值按真实分布定，2.1 的数字只作起点。
- **出现一次「发得太快」造成的实际损害。** 2.3 就要重判——但要的是**一次记录在案的损害**，不是「感觉太多」。
- **出现一次不该发生的跨项目发送。** 2.4 重判。同样要实例，不要设想。
- **威胁模型从「同机可信」变了。** 第一节整段作废，届时要的是硬控制而不是这一层，且那是另一个数量级的工程。

## 六、实施前置

本稿是 design only。要进入实施，**必须先有**：

1. **看板上线并跑出一段真实数据**（决策 4 的顺序，非可选）；
2. 一份定了阈值的实施稿，走用户 gate；
3. 阈值的**来源**写进那份稿子——是哪段时间、哪些 lane 的分布算出来的。⚠️ 一个没写来源的阈值，半年后没人敢动它，因为没人知道它当初凭什么是那个值。
