# 知识库需求

**状态：** 2026-10-20 需求稿。内容是问答议题 `a8d8110d` 里用户确认的第一版范围，不是技术设计，也不授权实现。

同日修订：早先草稿要管住现有的分散语料（规范仓、各项目记忆、角色说明），因此带出了知识位置清单、守门、负责人通知、跨仓总览等事项。用户指出知识库是一个单独的东西，不该自顶向下设计，第一版只要「引入 llm wiki，然后做一个检索工具和录入工具」。上述事项随之撤下，见第 3 节。

背景调研见 [知识过期：现状核对与成熟做法调研](2026-10-20-knowledge-staleness-research.md)，下文简称「调研稿」。

## 1. 目的

用户最痛的是 **agent 不能有效地更新知识**：新结论出来了，旧结论还留在原处被读到。调研稿里最典型的例子是 `cc`：

- 通用手册写着「Router 拒收 `cc`」；
- mocap 项目的记忆早已更正为「`cc` 已通」；
- 两处互不相通，手册一直没改。

用户提出的解法是：录入知识时，先搜相同或相似的知识，再决定要不要更新版本。知识采用 wiki 形态，用户原话是「其实我觉得wiki是真的挺适合的」。

## 2. 已确认需求

### R1：一个单独的 LLM wiki

知识库是独立的一处，采用 LLM wiki 形态：
- 一个主题一页，有新结论就改那一页，不让新旧两份结论并存；
- 有一个列出全部页面的目录页。

它作为 lane-router 插件里的知识资源存在，做法照图资源：独立于任何 lane，多条 lane 都能读写。

### R2：检索工具

lane 用它按意思查找相关页面，不要求字面一致。调研期间用通用仓现有的关键词检索 `kb.py query` 试过三次，只有一次在前 3 条里命中了要找的段落：搜「cc 拒收」时，「CC」先命中了圈复杂度和 CCache。所以只靠关键词不够。

### R3：录入工具，先检索再写

lane 用它把一条知识写进 wiki。它按固定步骤执行，步骤由程序保证，不靠提示词让模型自觉遵守：

1. 先在 wiki 里检索相同或相似的页面；
2. 把命中的页面摆给写的人看；
3. 写的人选一种处理：
   - 改原页；
   - 把原页旧段标成「已被取代」，再写新的；
   - 确认没有重复，新建一页；
   - 不写；
4. 保存，旧版本保留可查。

### R4：改不改由写的人决定，不自动删改

录入工具只负责摆出命中的页面、执行写的人选定的处理，不自己判断该删什么。外部先例：Mem0 原先在写入时由 LLM 自动增、改、删，2026-04 退回到只新增（调研稿第二节）。

## 3. 第一版不做

- **不导入现有内容**：规范仓、各项目记忆、角色说明都不导入，wiki 从空的开始。以后要不要导入，用起来再说。
- **撤下的早先事项**：知识位置清单、守门（拦截绕过录入工具的直接写入）、页面负责人与挂标记通知、跨仓总览。它们都建立在「知识库就是现有分散语料」这个前提上，现已撤下，以后用起来发现需要再提。
- **其他不做的**：
  - 帮 agent 问答的 RAG；
  - 自动删改已有知识；
  - 页面声明依赖、对着代码或部署状态自动核对；
  - 多条 lane 大规模同时写入的协调。用户说没有这种需求，基本的并发安全在设计中处理。
- **不归本 lane 的**：
  - 规范仓内部的改进（调研稿第四节 A 组）归规范仓的负责 lane；
  - skill 市场调研已转给 `agent_coding_guidelines/main`（2026-10-20，消息 `a7dd0455`）。

## 4. 验收场景

| 场景 | 应看到的结果 |
|---|---|
| lane 录入一条 wiki 里没有相似内容的新知识 | 新建页面，目录页能看到它 |
| wiki 里已有「Router 拒收 `cc`」页，lane 录入「`cc` 已通」 | 录入工具先把那页摆出来；写的人选「改原页」后页面更新，旧版本可查 |
| 同上，写的人选「标旧写新」 | 旧段标为已被取代，并指向新内容 |
| 录入工具摆出的页面与要写的内容无关 | 写的人选新建，已有页面不变 |
| lane 用检索工具按意思找，比如「怎么一次发给多条 lane」 | 能找到讲 `cc` 的那页，即使字面不同 |
| 另一条 lane 读同一页 | 读到最新内容 |

## 5. 留给技术设计

下面这些由设计稿给出推荐方案，不需要用户先决定：
- wiki 页面存放方式：放成文件进 git，还是存进 Router；
- 旧版本怎么保留；
- 语义检索怎么做；
- 两个工具的参数和返回形状；
- 用户怎么查看 wiki；
- 并发写同一页时怎么处理。

## 6. 与现有项目的接缝

- **插件形态**：问答需求 R12 规定，通信 core 不反向依赖功能模块，也不承担模块专有的状态。知识库照此做成独立功能模块。
- **第二种资源**：图资源需求 R1、R2 提出了「资源」，并有意没抽通用资源平台。知识库是第二种资源，到设计时第一次有两个样本可以对比，再决定要不要抽、抽什么。
