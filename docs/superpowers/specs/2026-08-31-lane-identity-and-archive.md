# lane 身份与归档：加一个 id，把归档做成挪表

**状态：** 设计稿，用户 2026-08-31 确认走本方案。取代 [`2026-08-27-lane-retirement.md`](2026-08-27-lane-retirement.md) 的存储部分（软删标记与 `unretire`）；那份的前置检查、目录隐藏、投递拒绝、批量开窗跳过等行为**全部保留**。结构事实见 [`2026-08-31-storage-model-review.md`](2026-08-31-storage-model-review.md)。

**一句话：** `lane` 加一个代理 `id`，`address` 降为标签、只在**活着的 lane 之间**唯一。归档＝lane 行留下当身份锚、它自己 mailbox 里的消息与文件挪进归档表与归档目录。地址当场可复用，历史不混淆，没有反向动词。

## 术语表

| 词 | 含义 |
|---|---|
| 身份锚 | 归档后留在 `lane` 表里的那一行。不是开关，是让历史里的引用有处可指的记录 |
| 活着的 lane | `archived_at IS NULL` 的那些 |
| 自己的信 | 收件方是这条 lane 的消息。它的文件住在这条 lane 的 mailbox 目录里 |
| 别人的信 | 这条 lane 发给别人的消息。文件住在**收件方**目录里，归档时**不动** |

## 一、问题

### 1.1 前一版的根因：一堵自己砌的墙

[`2026-08-27-lane-retirement.md`](2026-08-27-lane-retirement.md) 写「硬删被存储结构堵死」，因此把删除实现成标记位 `retired_at`。**那个判断是错的**：外键禁止的是「删掉 lane 却留着引用它的消息」，不是禁止删除；「消息必须留在活表里」是设计时**自己加的**约束，被报成了下层的能力边界。

那个标记位派生出后面全部的别扭：每处读都要过滤、多一个反向动词 `unretire`、地址被永久占住。

### 1.2 `unretire` 从未恢复过任何东西

`retire` 会把活跃 binding 一并失效（`router-core.ts:251`，全库唯一调用点），而 `unretireLane` 只把列置回 NULL。所以 unretire 之后那条 lane「存在但没绑对话」，你**必然**还要开新对话 attach。它只是让人有资格去做本来就要做的事，却在词汇表里占一个永久的位置。**用户裁定：删掉，归档是终态。**

### 1.3 地址即身份，于是「名字」成了死结

`address TEXT PRIMARY KEY`，没有代理 id。所以「换个名字」和「换一条 lane」在存储里是同一件事，归档一条 lane 就永久烧掉那个名字。

围绕这个死结曾提出三个选择——接受同名混淆 / 改写别人手里的历史 / 承认名字烧掉——**三个都是坏的**。它们坏的原因是同一个：**都在回避「地址不该是身份」这件事**。

⚠️ 而当初否掉「加 id」的理由是**成本报错了**：拿它跟「什么都不改」比。真实基线是「拆外键在 SQLite 里本来就要建表重建、消息表本来就要迁」——**加一列 id 是在一次已经要做的重建上多做一点。**

## 二、范围基线

用户能做的事，与今天相比只多出两条：

1. **归档一条 lane**（行为与 08-27 稿一致：目录隐藏、发不进去、批量开窗跳过、前置检查不变），且它的消息与文件**离开工作集**；
2. **归档之后，同一个地址可以用来新建 lane**，而历史里新旧两条**分得开**。

不在范围内：还原归档、删除任何消息、按项目批量归档、改名、清理 transcript。

## 三、设计

### 3.1 `lane` 加 id，地址只在活着的之间唯一

```sql
CREATE TABLE lane (
  id TEXT PRIMARY KEY,                  -- uuid，跟 binding.id / message.id 同形
  address TEXT NOT NULL,
  project TEXT NOT NULL,
  role_description TEXT NOT NULL CHECK (length(trim(role_description)) > 0),
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL,
  model TEXT,
  archived_at INTEGER
);
CREATE UNIQUE INDEX lane_live_address_idx ON lane(address) WHERE archived_at IS NULL;
CREATE INDEX lane_project_address_idx ON lane(project,address);
```

**关键是那个部分唯一索引**：地址只在 `archived_at IS NULL` 的行之间唯一。这个 pattern 库里已经在用——`binding_active_lane_idx ON binding(lane_address) WHERE inactive_at IS NULL`，不是新发明。

于是同名的新旧两条 lane 可以共存，各有各的 id，**历史里天然分得开**。

⚠️ **随之而来的硬约束**：今天每一处按 address 查 lane 的地方，含义都变成了「**活着的**那条」，查询必须带 `AND archived_at IS NULL`。漏掉一处，就会在归档后随机查到墓碑行。这条要靠测试逐个钉，不能靠通读。

### 3.2 三条外键改成引用 id 并**保留**，只拆一条

判据是一句话：**这个字段会不会指向「已经走了、而引用还留在活表里」的东西。**

| 字段 | 处置 | 理由 |
|---|---|---|
| `message.sender_lane` | → `sender_lane_id`，**保留外键** | 归档时 lane 行**留下**当身份锚，所以别人手里那 2637 封的 sender 有处可指，不悬空 |
| `message.target_lane` | → `target_lane_id`，**保留外键** | 同上 |
| `message.ack_lane` | → `ack_lane_id`，**保留外键** | 同上（它结构上恒等于 target，见结构复看第八节第 7 条） |
| `binding.lane_address` | → `lane_id`，**保留外键** | binding 跟着身份锚留下 |
| `message.reply_to` | **拆掉外键**，保持 TEXT | 它指向的是**另一封信**，而那封信真的被挪走了。实测 831 封活着的回信会指向已归档的信 |

**留下身份锚，是四条外键得以保留的全部原因。** 前一版方案要拆两条，正是因为它假设 lane 行会消失。

### 3.3 归档搬什么、不搬什么

```
归档 <project>/<lane> ＝ 一个事务里：
  ① 它「自己的信」（target 是它的消息行）→ 复制进 message_archive，从 message 删除
  ② 它的 binding 全部置为失效（行留下，仍引用身份锚）
  ③ lane.archived_at = now                    ← 地址此刻起可被复用
  事务提交之后：
  ④ 那些消息的文件 → 移入归档目录，并回写归档行的 relative_path
```

**不搬**：它发给活着的 lane 的信（2637 封）。那些文件住在**收件方**的 mailbox 目录里，是别人的东西。它们的 `sender_lane_id` 继续指向身份锚。

`message_archive` 与 `message` 同列，**但没有任何外键**，另加一列 `archived_at`。归档表不参与任何活路径的查询。

### 3.4 ⚠️ 双写的崩溃窗口，与 `reconcile` 的修复职责

第 ③ 步与第 ④ 步之间进程死掉，会留下：**文件还在活的 mailbox 里，而它的行已经不在 `message` 表里。**

而 `reconcile` 今天对这种状态的处置是**当孤儿重新插回库里**（`mailbox-store.ts`）——归档会被静默撤销。

⇒ **`reconcile` 必须先查归档表再判孤儿**：

```
文件在、message 表里没有：
    id 在 message_archive 里  ⇒ 这是一次没做完的归档 ⇒ 把文件挪进归档目录（不插回）
    id 不在                   ⇒ 照旧当孤儿插回
```

**顺序不能反过来**（先挪文件再改库）：那样崩溃会留下「行在、文件不在」，而 `reconcile` 对这种状态是**抛损坏错误**，比静默撤销更难恢复。

⇒ **库先、文件后，`reconcile` 负责把文件收敛到库的状态。** 库是权威。

### 3.5 归档后同名新建：历史怎么读

新建的 lane 拿到**新 id**，与身份锚是两行。所以：

- 别人手里旧信的 `sender_lane_id` 指向**旧那条**，看板显示它时应显示旧那条的地址（同名，但可标注为已归档）；
- 新 lane 的信指向新那条。

**两条 lane 在数据上从不混淆**，混淆只可能发生在**呈现层**（两个同名地址并排）。看板对归档 lane 已有折叠区，同名时在旧那条后面标注归档时间即可。**这不需要改写任何既有数据。**

### 3.6 `reply_to` 悬空之后怎么读

拆掉外键后，831 封回信的 `reply_to` 会指向已挪走的信。这是**诚实的**——它回复的那封确实归档了。

⇒ 读取方必须能分清三态，不能把后两者混成一个：

| `reply_to` | 含义 |
|---|---|
| `NULL` | 这封信不是回信 |
| 有值，且 `message` 里查得到 | 正常 |
| 有值，但 `message` 里查不到 | **它回复的那封已归档**（可在 `message_archive` 里找到） |

### 3.7 保持不变的

前置检查（在线不让归档、有未读信不让归档）、目录隐藏、投递拒绝、批量开窗跳过、`list-archived`、错误文案里给出的出路——按当前实现保留。

### ⚠️ 一处例外：attach 到已归档地址，**建新 lane**

本稿初版在这里写着「attach 拒绝已归档地址，行为逐字不变」，**那跟验收 2（同地址可新建）直接互斥**——`lane_attach_current` 是唯一的建 lane 路径，它继续拒绝，整份改造就白做。实施期由 `lane-router/impl` 当场发现并交用户裁定，**用户 2026-08-31 确认：attach 到已归档地址新建一条 lane（新 id），旧那条永远回不来。**

⇒ 真正要保的不变量不是「拒绝」，而是：**没有任何路径能让已归档的 lane 回到在役。** 新建一条同名的 lane 不违反它——那是另一条 lane。

📌 **根因值得记住**：初版那句是一条**兜底条款**（「其余全部按现状保留」）。兜底条款会把改造自己要打破的那条行为也一并保住，而且**读起来毫无异样**。⇒ 写「其余不变」时，要逐项对着改造目标核一遍，不能整句带过。

## 四、迁移（v5 → v6）

SQLite 改不了已有外键定义，必须**建表重建**。库里已有 v1→v2 的先例（`schema.ts:150-172`），包括 `foreign_keys` 的开关舞步——⚠️ `database.ts:10` 无条件 `foreign_keys = ON`，重建期间必须按那个先例临时关掉再恢复。

步骤：

1. 建新 `lane`（含 `id`），为每条现有 lane 生成 uuid，`retired_at` 的值原样搬进 `archived_at`；
2. 建新 `binding`、新 `message`，**按 address 关联**填入对应的 `lane_id` / `*_lane_id`；
3. 建 `message_archive`（空）；
4. 丢弃旧表、改名新表、重建全部索引（含新的部分唯一索引）。

**必须保住的量**（当前值，迁移测试要逐条断言）：lane **25**、binding **63**、message **4637**、其中 `retired_at` 非空的 **5** 条成为身份锚。

⚠️ **已归档那 5 条的地址此刻起不再占用唯一索引**——迁移之后立刻可以新建同名 lane。这一条要有测试，因为它正是整份改造要买的东西。

### ⚠️ 迁移只搬标记，不搬信：存量归档是「没做完的归档」

本稿初版在这里漏了一件事，**2026-08-31 真机迁移后实测发现**：迁移把 `retired_at` 转成了身份锚，但**「把信与文件挪出工作集」是新 `archive` 操作的行为，迁移不会追溯执行它**。

实测结果：5 条身份锚名下 **2140 封**信（render 816 / ui 650 / arch 354 / review 236 / hotfix 84）仍在活表与活的 mailbox 目录里，`message_archive` 为 0 行。地址确实释放了、数据也没坏（0 pending、无外键违规），但**归档要买的东西对这 5 条没买到**。

⇒ **修法：让 `archive` 对一条已归档的 lane 补做尚未完成的步骤**，而不是早退。用户跑一次命令补齐一条。

三个被否掉的替代：**新增一个「修复」动词**（多一个面，而这件事概念上就是「继续归档」）、**启动时批量修**（把一次重启变成搬 2140 个文件的漫长 I/O，而 Router 启动在每次 `ensureRouter` 的关键路径上）、**在迁移里追溯执行**（迁移跑在 DB 初始化里，不该做文件 I/O）。

📌 顺带买到一个本来就需要的性质：**归档从此幂等、可续做**。§3.4 的崩溃窗口修复管的是「行已挪、文件没挪」，本条管的是「标记已打、行和文件都没挪」——**同一件事的两个阶段**，做完之后任何阶段中断都能靠再跑一次补齐。

## 五、验收标准

1. `lane` 有 `id` 主键；`address` 非唯一，但**活着的 lane 之间**唯一——两条 `archived_at IS NULL` 的同地址行插入被拒。
2. 归档一条 lane 之后，**用同一个地址新建成功**，且新旧两行 id 不同、旧行 `archived_at` 非空。
3. `message.sender_lane_id` / `target_lane_id` / `ack_lane_id` 与 `binding.lane_id` 均为指向 `lane(id)` 的外键；`reply_to` **不是**外键。
4. 归档把「自己的信」的行移入 `message_archive`、从 `message` 删除；「别人的信」行数不变、`sender_lane_id` 仍指向身份锚。
5. 归档把那些信的文件移入归档目录，并回写归档行的 `relative_path`；活着那端的 mailbox 目录**文件数不变**。
6. 库改完、文件未挪时运行 `reconcile`：文件被**挪进归档目录**，**不**插回 `message` 表。
7. 文件挪完、库未改这种状态**不会由归档产生**（顺序是库先文件后）；若人为造出，`reconcile` 仍按既有规则报损坏。
8. 每一处按 address 查 lane 的读路径都只返回活着的那条；归档后按该地址查，返回「不存在」而不是墓碑行。
9. 前置检查、目录隐藏、投递拒绝、批量开窗跳过、`list-archived` 行为与改造前**逐字一致**；attach 到已归档地址**新建一条 lane**（新 id），且**没有任何路径**能让已归档的那条回到在役。
10. 迁移保住 lane 25 / binding 63 / message 4637 / 身份锚 5；迁移后立刻可用那 5 个地址新建。
11. 无 `unarchive`：CLI 报 Usage、`POST /lanes/unarchive` 返回 404。
12. 对话工具数量、名称、参数不变；无新增 RPC 方法；除已有的 lane 管理端点外无新增 HTTP 端点。

## 六、验证方法

- **同地址共存**：造一条 lane、归档、同地址再建，断言两行 id 不同（2）；再试插入第二条**活着的**同地址行，断言被拒（1）。
- **搬与不搬**：造 A、B 两条 lane，A↔B 互发若干封，归档 A，断言 `message_archive` 只含 target 为 A 的那些、`message` 里 target 为 B 的那些**一封不少**且 sender 仍指向 A 的身份锚（4）。
- **文件两侧都数**：归档前后分别数 A 目录与 B 目录的文件数（5）。**只数库会漏掉「删了行没挪文件」。**
- **崩溃窗口**：手工制造「行已挪、文件未挪」，跑 `reconcile`，断言文件进归档目录且 `message` 表**没有多出行**（6）。这条**先造红**——把 reconcile 的归档查询去掉，它必须变成「插回一行」。
- **读路径**：对每一个按 address 查 lane 的入口各写一条「归档后查该地址返回不存在」（8）。这条要枚举入口，不能通读代码判断。
- **迁移**：在 v5 fixture 上跑，断言四个数与身份锚（10）；**空库与有数据两侧都造**——只测空库的话，实现成「重建时丢数据」也全绿。
- **变异检验**（每条先说凭什么会红）：部分唯一索引写成全表唯一（同地址新建会被拒 ⇒ 杀 2）；归档不删 `message` 行（杀 4）；`reconcile` 不查归档表（杀 6）；读路径漏掉 `archived_at IS NULL`（杀 8）；迁移不搬 `retired_at` 的值（杀 10）；`reply_to` 保留外键（归档含被回复的信时事务失败 ⇒ 杀 4）。

## 七、明确不做

- **不做还原。** 没有 `unarchive`，没有任何把身份锚变回活着的路径。
- **不删除任何消息。** 归档是挪走，不是删。
- **不动别人手里的历史。** 那 2637 封的 `sender_lane_id` 保持原样。
- **不清理 transcript。** 实测 487 个文件 1005 MB，与本设计无关，仍是独立的下一个迭代。
- **不改 `ack_lane` 的冗余。** 已知它结构上恒等于 `target_lane`（结构复看第八节第 7 条），本轮拆表已经够大，留作将来简化的第一个候选。
- **不做按项目批量归档、不做改名。**

## 八、会推翻本稿的事

- **归档之后仍然需要读回旧数据。** 那说明归档表不该与活表隔离，要重谈。
- **同名新旧两条 lane 在呈现层持续造成误读。** 那要的是呈现层的区分手段（3.5），不是回到烧掉名字。
- **`reconcile` 的双向不对称被改掉。** 3.4 的崩溃窗口修复建立在「库是权威、文件向它收敛」之上，那条前提变了要重看。
