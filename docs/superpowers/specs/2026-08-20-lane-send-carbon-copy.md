# `lane_send` 的抄送 设计

**状态：** 2026-08-20 用户批准并已实现。自动测试与变异检验已通过；第六节两条手工用例**尚未跑**，原因见 `docs/manual-tests.md` 的 `TC-CC-1` / `TC-CC-2`——在它们通过之前，抄送不得被称作真实链路已验证。实施期推翻了初稿 3.2 节的一处论证，已就地更正并标注。

**一句话结论：** 六条 lane 长期在正文里写「(抄 arch / ui)」，而 `lane_send` 只有一个收件人、Router 从不解释正文，于是这些副本**一封都没送到过**，且发信与被抄双方都收不到任何信号。本设计给 `lane_send` 加一个 `cc` 参数，一次调用生成 N 份**各自可 ack** 的独立消息；顺带修掉两处同族的静默失败——发信回执与投递结果无关、以及一个不给出路的跨项目拒绝。不新增工具、不新增数据表、不做数据库迁移、不解析消息正文。

## 术语表

| 术语 | 含义 |
|---|---|
| 抄送（cc） | 一次 `lane_send` 把同一段正文投给多条 lane。参数名沿用邮件的习惯。 |
| 副本 | 抄送产生的每一份消息。本设计中副本是**完整的独立消息**，有自己的 id、自己的 mailbox 文件、自己的 ack。 |
| 收件人清单 | 一次抄送的全部收件人（`target` 加 `cc`）。它是消息内容的一部分，写进文件头。 |
| 派生 request key | 由调用方的 `requestKey` 加收件人地址确定性拼出的键，用来让每份副本各自去重。 |
| 回执 | `lane_send` 的返回值。今天它是通知发生**之前**的快照。 |

## 一、问题

### 1.1 一个从不存在的机制，被当成存在的

`lane_send` 的参数是 `target` / `body` / `kind` / `reply_to`——**只有一个收件人**。而 Router 不解释正文（通知连正文都不带，有测试钉着）。所以正文里写的「抄 X」对系统而言不存在。

⚠️ 它能整轮不被发现，是因为**两侧都不产生信号**：

| 谁 | 看到什么 | 于是以为 |
|---|---|---|
| 发信方 | 对 `target` 的投递成功 | 副本也到了 |
| 被「抄」的一方 | **什么都没有** | 没有信可读，不会去问 |

⇒ 这不是「偶尔漏一封」，是一个不存在的机制被当成存在，而它的失效是静默的。

**实测规模**（2026-08-20 由 `mocap/render` 转来，各 lane 自数信箱）：arch 发出 69 / 12 / 11 封中一大批写着「抄」，hub 带「抄」的 35 封，render 181 封里 12 封——合计约 59 封副本全部未投递。

**一次可量化的代价**：用户在 arch 那条对话里裁了三条布局决定，arch 写「(抄 render / ui)」发给 hub。render 在自己信箱里搜那封的 id，零命中。于是它在给用户的汇报里把一件**已被裁掉**的事列成「最卡的一件」——在用户那边读起来是「我的决定没生效」。

> 口径：上述数字与那次误报由 `mocap/render` 转述（各 lane 自数），本 lane 未复核；`lane_send` 无 cc、Router 不解释正文两条为本 lane 实测。

三方目前的权宜是「逐条 lane 分别发，不写抄」。它把成本转成 N 倍的发信动作，且**没有任何东西阻止下一个人继续写「抄 X」**。

### 1.2 回执与投递结果无关（本 lane 查出，比来信所述更广）

来信把「回执读起来像排队中、实际永远不会有人被叫醒」记为跨项目或无通道特有。核查根因后**它是普遍的**：

```ts
const stored = state.insertMessage(...);      // 快照在此刻取
await this.dependencies.pump.notifyLane(target);
return stored;                                // 返回的是通知之前那份
```

而 `NotificationPump.recordOutcome` 明明把真实结果写回了那一行。⇒ **回执里的 `notificationState` 恒为 `pending`，对所有发信一律如此**——投递成功的、没有通道的、发送出错的，发信方看到的回执一模一样。

这正是 2026-08-10《带原因的健康检查》点名的问题 #1；那轮的修法落在数据库列与 `reach` 上，**没落在返回值上**。

### 1.3 一个不给出路的拒绝

`lane_restore_project` 拒绝跨项目（`RESTORE_LANE_OUTSIDE_PROJECT`），这是 2026-08-13 稿明写的非目标，**判断本身正确**。但错误信息与工具说明都止于「不在本项目」，不告诉调用方出了这个范围该怎么办。

⇒ 实测后果：`mocap/render` 据此得出「我开不了 `lane-router/design` 那条对话，要用户手动开」，并把它写进了跨项目来信。**该结论不成立**——`lane-router-lane open <project>/<lane>` 是已构建、已全局 link 的 CLI，其调用链（launcher 用合成身份、`/lanes/resume-info` 端点）**全程没有项目作用域**。本 lane 实测：跨项目查询返回了完整的 `conversationId` 与 `cwd`，阴性对照（不存在的 lane）返回 `{"state":"missing"}`。

⇒ 信息本身不缺：`techniques/lane-router.md` 111-112 行有完整用法、222-225 行有排查表，且该手册所在语料由全局 `CLAUDE.md` 链接、每个会话可达。缺的是**失败点上的指针**——工具拒绝它的那一刻，恰好是唯一没有指路牌的位置。

## 二、范围基线

按 `auditing-plan-scope` Phase A，在不看候选方案的前提下记录。

**用户要的结果：** 一条 lane 想把同一段话同时给几条 lane 时，它们真的都收到；且发信方不必靠约定和自律来保证这件事。

**当前用户流程：** lane 要把一个结论同时告诉 N 条 lane → 今天要么在正文里写「抄 X」（静默失效），要么手工发 N 次（成本 N 倍，且不阻止下一个人写「抄」）。

**信任模型：** V1《目标与边界》已定的同机可信个人环境，本设计不改动。

**满足该流程的最小可观测行为：** 一次调用把同一段正文送进 N 个信箱，每份可被各自的收件人独立读取和 ack；收件人能看出这封信还发给了谁；发信方拿到的回执能区分「送到了」与「没有通道」。

这条基线**不包含**：发送者身份类别（用户 vs lane）、正文解析、消息分组、投递状态聚合、抄送的权限语义。前两项已由用户在 2026-08-20 明确裁掉，理由见第七节。

## 三、设计

### 3.1 cc 的语义：N 份独立消息，不是 1 份共享

```jsonc
lane_send({ target: "mocap/hub", cc: ["mocap/render", "mocap/ui"], kind: "normal", body: "..." })
```

产生 **3 份消息**，各有独立的 id、独立的 mailbox 文件、独立的 `pending` → `resolved` 生命周期。

**为什么不是 1 份共享：** 每条 lane 的处理进度不同（这是消费侧的原话需求），而 `ack` 的归属判定是 `message.targetLane === binding.laneAddress`——共享一份就必须给 ack 引入「部分完成」状态，那是一个新的状态机。N 份独立消息则**完全不动 ack 一行代码**。

**被 cc 的一方 ack 了对发信方意味着什么：** 只意味着那一条 lane 处理完了它自己那份。本设计**不提供**跨副本的聚合视图（见第四节）。

**收件人集合**去重后处理：`target` 与 `cc` 指向同一条 lane 时只产生一份。**全部收件人必须在写入任何一份之前校验通过**（lane 存在、地址合法）——一处不合法则整次调用失败且什么都不写，保持「响亮失败、不留半截」。

**跨项目**：cc 沿用 `target` 今天的规则，不做新的作用域决定。`send` 今天允许跨项目投递，cc 同样允许。

### 3.2 幂等：派生 request key

`request_key` 上有 `UNIQUE` 约束，而一次调用只带一个 `requestKey`。每份副本的键按收件人**确定性派生**：

```
<调用方 requestKey>#<收件人地址>
```

去重逐份独立进行：查得到的跳过，查不到的写入，最后返回全部 N 份。

**这一点不是锦上添花。** 2026-08-12 落地的 RPC 重绑（`cfbbe76`）在连接被拒时会重试一次，其安全性正是建立在 `lane_send` 可重放之上。派生键确定性 ⇒ 重放产生同样的键 ⇒ 去重照常生效。

两条已用变异检验坐实的性质：**键必须确定性**（改成随机后，重放立刻产生重复副本），**且必须逐收件人派生**（整次调用共用一个键时，第二个收件人会撞上第一个的记录，三条测试同时变红）。

> **诚实边界（实施期实测，与初稿的说法不同）：** 初稿写的是「若改用索引拼接（`#0` / `#1`），收件人顺序一变就会重复投递」。**这条站不住**——实测把键改成按位置拼，全部测试仍然通过。原因是真实重放会原样重发同一份请求体，收件人顺序**不会**变；而返回的记录是从库里重读的，各自带着自己存储的 `targetLane`，所以连归属也不会错乱。
>
> ⇒ 按地址派生仍然是本设计的选择，理由改为**构造上就与顺序无关、不依赖「重放必然同序」这个前提**，而不是「修了一个谁踩过的坑」。对应的测试也已改名——它验的是重放免费，不是顺序无关。

同样的性质让崩溃后的半截状态自然收敛：已写的跳过、缺的补上，新鲜调用与重放走**同一条代码路径**，不需要为部分完成写特例。

### 3.3 收件人清单要对收件人可见

每份副本的文件头增加一行：

```
cc: mocap/hub, mocap/render, mocap/ui
```

**为什么它属于最小范围而不是锦上添花：** 1.1 节那次误报里，arch 写「抄 render / ui」的**目的**就是告诉 hub「这两条也知道了」。收件人清单本身就是被传递的信息；只投递不显示清单，会立刻长出同一族的困惑（「arch 也收到了吗，我要不要再转一遍」）。

它**不进数据库**：没有查询需要它，`message` 表结构不变，因此**没有 schema 迁移**。`parseMessage` 把全部 header 收进 map 后只读它认识的几个，未知 header 不报错——已实测，所以旧文件与新文件互相兼容。

### 3.4 回执说真话

`send` 在通知全部发出之后**重读每一行**再返回。于是 `notificationState` 是这次投递的真实结果（`sent` / `deferred` / `no_channel` / `send_failed`），而不是恒为 `pending` 的快照。

⇒ 1.3 节想要的那个信号**自动落地、不需要任何特判**：目标没有通道时，发信方直接看到 `no_channel`。跨项目也不必单独判定——跨项目的目标若在线就是 `sent`，离线就是 `no_channel`，与同项目同一套语义。

**顺序**：先写全部副本，再逐个通知。否则第一个收件人可能在其余副本落盘之前就被唤醒。

**返回形状改为数组**（单收件人时是单元素数组）。这是本设计**唯一的破坏性变更**：今天返回单个记录对象。选数组而非「有 cc 时数组、没有时对象」，是因为随入参变形的返回值是个陷阱；消费方是读 JSON 的 agent，一致的形状比兼容旧形状更重要。

### 3.5 把指针挪到失败点

两处字符串，无新机制：

1. `RESTORE_LANE_OUTSIDE_PROJECT` 的消息追加出路：`; open it from a shell with: lane-router-lane open <address>`
2. `lane_restore_project` 的工具说明补一句：跨项目请用该 CLI

⇒ 跟本设计其余部分同一条主线：**响亮的失效优于静默的，而一个不给出路的拒绝等于半个静默失败**。

## 五、验收标准

1. 一次带 `cc` 的 `lane_send` 在每个去重后的收件人 `pending` 目录各产生一份文件，各有不同的 message id。
2. 每份副本可由**它自己的**收件人 ack；一份被 ack 不改变其余副本的状态。
3. 任一收件人地址非法或 lane 不存在时，整次调用失败，且**没有任何文件或数据库行被写入**。
4. 同一 `requestKey` 重放同一次调用，不产生第二批副本，且返回与首次相同的 N 份记录。
5. 收件人顺序变化不改变派生键，因而不产生重复投递。
6. 每份副本的文件头含 `cc:` 行，列出全部收件人；不含 `cc` 的旧文件仍能被 `reconcile` 正常解析。
7. 返回值是数组；不带 `cc` 时是单元素数组。
8. 返回的 `notificationState` 是本次投递的真实结果：目标在线为 `sent`，无通道为 `no_channel`。
9. `message` 表结构不变，`ROUTER_SCHEMA_VERSION` 不变，无迁移。
10. 工具数量与名称不变；无新增 RPC 方法、HTTP 端点、命令行参数或配置项。
11. `RESTORE_LANE_OUTSIDE_PROJECT` 的消息含可直接复制执行的 `lane-router-lane open <address>`。
12. `ack` 的实现代码不被本设计改动。

## 六、验证方法

自动测试覆盖第 1–12 条中除第 8 条真实通道部分外的全部：

- **各自可 ack**：两个收件人，ack 其中一个，断言另一个仍在 `pending` 且其文件未移动。
- **全有或全无**：收件人清单里放一个不存在的 lane，断言抛错**且** `pending` 目录文件数与数据库行数与调用前逐一相等。这条要数**两侧**——只数数据库会漏掉「写了文件没写行」的半截状态。
- **重放幂等**：同一 `requestKey` 调两次，断言副本总数不变且两次返回的 id 集合相同；再把收件人顺序颠倒重放一次，断言仍不新增。⚠️ 最后这一步**不能分辨按地址派生与按位置派生**（见 3.2 节的诚实边界），它只是多覆盖一种重放形状，不承担取舍论证。
- **回执说真话**：一个收件人在线、一个无通道，断言同一次调用返回的两份记录 `notificationState` 分别是 `sent` 与 `no_channel`。**这条是本设计的牙**：没有它，实施成「照旧返回快照」也能让其余测试全绿。
- **旧文件兼容**：手写一份不含 `cc:` 的文件放进 `pending`，跑 `reconcile`，断言正常入账。
- **不改投递时机**：与 2026-08-10 稿同一条不变量——`notifyLane` 选中的消息集合不因 `cc` 的存在而改变。

**变异检验**（照 `cfbbe76` 那轮的三态做法：变异前绿、变异后红、还原后绿）。实施期实跑结果：

| 变异 | 结果 |
|---|---|
| 回执改回通知前快照 | 杀掉「回执说真话」一条 |
| 「全部校验后再写」改成「边校验边写」 | 杀掉「全有或全无」一条 |
| 派生键改成随机 | 杀掉「重放幂等」与既有的单发去重两条 |
| 整次调用共用一个键（不逐收件人派生） | 杀掉三条 |
| **派生键改成按位置拼** | **全部存活** —— 见 3.2 节诚实边界；该取舍没有可展示的失败路径 |

自动测试**覆盖不到**、必须进 `docs/manual-tests.md`：

| 用例 | 为什么机器测不了 | 怎么做 |
|---|---|---|
| 被 cc 的真实 lane 确实被唤醒并读到正文 | 需要真实 Claude 会话与 channel | 从一条 lane 发一封 `cc` 两条在线 lane 的消息，确认两条都自行开出 turn、各自读到 `cc:` 清单、各自 ack |
| 跨项目 cc 的收件人 | 需要两个项目各有在线 lane | 同上，收件人跨项目，确认回执为 `sent` 而非 `no_channel` |

## 七、明确不做

- 不新增对话工具、HTTP 端点、命令行子命令、配置项或数据表；不做数据库迁移。
- **不解析消息正文**：Router 存正文但从不解释它，本设计不打破这一点。
- **不引入发送者身份类别**：转述能传事实、传不到权限，这条边界由人在目标对话里当面确认来兜，不由 Router 表达。使用者不应认为 cc 能把用户的授权带到别的 lane。
- 不做副本分组、跨副本聚合状态、投递回执的持久化聚合。
- 不改 `ack` 语义、`generation` 规则、通知投递时机或 `reach` 字段。
- 不裁定 `send` 与 `lane_restore_project` 的作用域方向（见第四节 `Defer`）。
