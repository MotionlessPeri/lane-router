# 议题页：两栏在一屏内各自滚动 —— 需求与设计

**状态：** 需求与设计合一稿，2026-10-19 由 `lane-router/inbox` 起草。布局方向和打开议题时停在哪里，用户已在议题收件箱上确认（议题 `2a5887bd`，条目 #4）；整份稿子用户已审过，回复「没问题，实现吧」（同一议题条目 #9，2026-10-19）。实施归 `lane-router/impl`，第五节是验收标准。Vikunja #332。

## 术语表

| 词 | 含义 |
|---|---|
| 议题页 | `/issues`，即 `src/ui/issues/index.html`。整页是一个静态 HTML，CSS 和脚本都内联在里面 |
| 两栏框 | `.columns`。左栏是议题列表 `.list-panel`，右栏是议题详情 `#issue-detail` |
| 历史区 | 右栏中间的讨论历史：问题状态 `#questions`、条目 `#history`、「继续加载历史」按钮 `#load-history` |
| 回复区 | 右栏底部的回复表单 `#compose`，加上状态行 `#read-status`、`#operation-status` 和重试按钮组 `#operation-recovery` |
| 未读条目 | 满足 `author = lane`、`kind ≠ event`、`seq > thread.readSeq` 的条目。口径与列表的「未读答复」标记相同（`src/modules/issues/store.ts:59`） |
| 宽屏 / 窄屏 | 以现有断点 680px 为界 |

## 一、问题与结论

两栏框只设了 `min-height: 590px`，没有高度上限，左右两栏也都没有自己的滚动区（`index.html:33-43`），所以议题有多长，整页就有多长。回复区排在历史的最后，讨论一长，就要翻到页底才能回复。

还有一层：每次轮询成功（5 秒一次），页面都用 `replaceChildren` 重建整段历史（`index.html:326-339`）。整页滚动时看不出问题；改成框内滚动以后，这会直接冲掉阅读位置，正文里选中的文字也会被清掉。

结论（宽屏）：

1. 两栏框撑满视口剩下的高度，整页不再随内容变长。
2. 左右两栏各自滚动。
3. 右栏分三段：标题栏固定在顶部，回复区固定在底部，只有历史区滚动。
4. 轮询不打断阅读：滚动位置和选中的文字都不变。
5. 打开议题时，停在第一条未读条目的开头，并在它前面画一条「以下是新内容」分隔线；没有未读，就停在最新一条。

窄屏保持现状，仍是整页滚动。

## 二、选型

| 选择 | 采用 | 理由 |
|---|---|---|
| 高度按视口剩余算，不写死像素 | 是 | 把用户的两种说法合成一种。换显示器不变形，切换长短不同的议题时框的大小也不跳 |
| 两栏框高度下限 420px | 是 | 视口很矮时（例如开着开发者工具），框不会小到看不见内容；低于下限时允许整页滚一点 |
| 右栏只滚历史区，标题栏和回复区固定 | 是（用户确认） | 整栏一起滚的话，回复区还在内容最后，痛点只解决一半 |
| 回复区默认紧凑，聚焦或有草稿时展开 | 是 | 固定的回复区直接占用历史区高度。按 1080p 屏估算：视口约 950px，页头到筛选条约 270px，两栏框约 680px。现在的回复区（标签、选择框、100px 输入框、按钮行）约 230px，会把历史区压到 360px 左右；收起后约 120px |
| 左栏也单独滚 | 是 | 左栏一页最多 100 个议题，议题多了一样会把页面拉长 |
| 轮询改为增量渲染：只追加新条目，问题状态和投递事实只在变化时更新 | 是 | 条目只追加、不改写，没有必要每 5 秒重画一遍。增量渲染能同时保住滚动位置和选中的文字；只保存并恢复 `scrollTop` 保不住选中的文字 |
| 打开议题时停在首条未读的开头 | 是（用户确认） | lane 的答复经常很长（真实数据里正文长度 p90 约 1500 字），停在最底下看到的是答复的结尾 |
| 新内容分隔线 | 是 | 让人看得出为什么停在这里。`thread.readSeq` 已经在详情响应里，不用改后端 |
| 窄屏也框内滚动 | 否 | 手机上框里套框很难用。窄屏另有问题（选中议题后不会滚到详情），不在本稿 |

## 三、设计

### 3.1 布局（宽屏）

- 页头、标题、说明、筛选条、列表状态行照旧排在上方；两栏框占满剩下的视口高度，下限 420px。
- 左栏：议题列表和「加载更多议题」在左栏内滚动。
- 右栏：
  - **标题栏（固定）**：标题、元信息、「结束议题」按钮，展开时的结束确认框，以及详情读取失败的提示 `#detail-status`。
  - **历史区（滚动）**：`#questions`、`#history`、`#load-history`。
  - **回复区（固定）**：回复表单、`#read-status`、`#operation-status`、`#operation-recovery`。状态行和重试按钮不能被滚出视野。
  - 没有选中议题时，右栏只显示「选择一个议题，查看完整讨论。」。
- 历史区可以用键盘聚焦和滚动（`tabindex="0"`），保留 `aria-label="讨论历史"`。

### 3.2 回复区的紧凑形态

- **收起**：输入框两行高；「回复对象」选择框和「发送回复」按钮放在同一行，回复区总高约 120px。
- **展开**：输入框获得焦点、草稿不为空、有正在进行或结果未确定的操作，满足其一时，输入框展开到约 6 行。失焦且草稿为空时收起。
- 用户可以手动拖大输入框，但回复区最高不超过右栏高度的一半。
- 议题已结束时，回复区只剩「议题已结束。讨论历史保留。」一行。
- 「回复对象」的默认值和选项，本稿不改（见第七节）。

### 3.3 轮询与重画

- 历史区按 `seq` 增量渲染：已经渲染的条目不重建，新条目追加到末尾；问题状态和投递事实只在内容变了时更新对应的节点。
- 左栏也一样：轮询结果和当前渲染一致时不重建；有变化时更新，并保持左栏的滚动位置。
- 效果：轮询后，历史区和左栏的滚动位置都不变，用户在正文里选中的文字也还在。
- 副作用：代码块复制按钮的「已复制」不会再在 5 秒后复原，改为下次选中这个议题时复原。仍然不为这件事加计时器，沿用页面现有的约定：计时器只用于请求超时（`index.html:166-168`）。

### 3.4 定位规则（宽屏）

1. **打开议题**（从列表点选）：以这次选中后第一次从后端取回的详情为准，记下其中的 `thread.readSeq`。页面随后会标已读，所以必须在标已读之前取。
   - 有未读条目：在首条未读条目前插入分隔线「以下是新内容」，然后滚动，让分隔线位于历史区顶端。
   - 没有未读条目：滚到历史区底部。
2. **切回本页里看过的议题**：先恢复离开时的位置（用缓存的详情先画出来时就恢复）。第一次取回新详情后，如果有未读条目，按规则 1 定位到首条未读。
3. **跟随新内容**：轮询带来新条目时，如果更新前历史区在底部（距底部 ≤ 40px），更新后保持在底部；否则位置不动。
4. **自己发出回复**：保存成功、重新读取之后，滚到底部，让新回复可见。
5. **回复区展开或收起**：如果历史区原本在底部，保持在底部。
6. 分隔线只在打开那一刻计算，之后不随已读推进而移动。切到别的议题再回来时，按规则 2 重新判断。
7. 首条未读条目还没加载时（议题超过 100 条，而详情从最旧的一页开始取，见 `index.html:276-286`），滚到已加载内容的底部，不画分隔线。

### 3.5 代码落点

| 位置 | 改动 |
|---|---|

## 四、范围审计

| 候选面 | 使用者与频率 | 依据 | 删掉的后果 | 现有替代 | 处置 |
|---|---|---|---|---|---|
| 两栏框撑满视口 | 用户，每次看长议题 | 用户需求 | 页面继续被拉长 | 无 | 保留 |
| 左栏单独滚 | 用户，议题多时 | 同上 | 议题多时页面照样被拉长 | 无 | 保留 |
| 标题栏和回复区固定 | 用户，每次回复 | 用户确认 | 回复还得翻到底 | 无 | 保留 |
| 回复区紧凑形态 | 用户，每次看议题 | 固定的回复区占高度 | 笔记本屏幕上历史区只剩一半左右 | 无 | 保留 |
| 增量渲染 | 每 5 秒一次 | 框内滚动后，阅读位置会被冲掉 | 读到一半位置跳走，选中的文字消失 | 保存并恢复 `scrollTop`（保不住选中的文字） | 保留 |
| 打开时定位到首条未读 | 用户，每次打开 | 用户确认 | 每次都要自己找新内容 | 无 | 保留 |
| 新内容分隔线 | 用户，打开有未读的议题时 | 让定位看得懂 | 停下的位置看起来很随意 | 无 | 保留 |
| 切回时恢复位置 | 用户，对照两个议题时 | 每个议题已有独立的视图状态（草稿就存在 `views` 里） | 切回来就跳到底部或未读处 | 规则 1 | 保留 |
| 不在底部时显示「有新内容」浮动按钮 | 无 | 无 | 下方来了新内容没有提示 | 列表的「未读答复」标记 | 推迟 |
| 窄屏框内滚动 | 无 | 无 | — | 整页滚动 | 删除 |
| 超长议题虚拟滚动 | 无 | 真实数据最长 24 条 | — | — | 删除 |

## 五、验收标准

第 1–8 条在真实浏览器里自动测（宽屏视口 1280×800，窄屏 375×800）；第 9–11 条在 happy-dom 里测；第 13 条是真机。

1. 宽屏下打开一个 60 条、每条几百字的议题：文档的可滚动高度不超过视口高度（`document.scrollingElement.scrollHeight ≤ innerHeight`），历史区的 `scrollHeight > clientHeight`。
2. 同一状态下，标题栏和回复区（含「发送回复」按钮）的包围盒都完全在视口内；历史区滚到顶和滚到底时，这两块的位置都不变。
3. 左栏有 100 个议题时，文档高度满足第 1 条的条件，左栏自身可以滚动。
4. 历史区滚到中部，点「刷新」（与轮询走同一条路径），且没有新条目：`scrollTop` 不变，左栏的滚动位置也不变。
5. 在正文里选中一段文字后点「刷新」：选区还在，选中的文字相同。
6. 历史区在底部时，后端追加一条 lane 条目，再点「刷新」：历史区仍在底部，新条目可见。历史区在中部时做同样的操作：`scrollTop` 不变。
7. 打开一个 `readSeq` 停在中间的议题：分隔线存在，紧挨在首条未读条目前面，分隔线顶边与历史区顶边对齐（误差 ±2px）。打开一个全部已读的议题：历史区在底部，没有分隔线。
8. 窄屏下打开第 1 条用的议题：文档高度大于视口（整页滚动，与现状相同），历史区没有自己的滚动条。
9. 回复区节点不在历史区节点内部；状态行 `#operation-status`、`#read-status` 也不在历史区内。
10. 轮询后，已渲染条目的 DOM 节点还是原来那个对象（增量渲染）；新条目追加在末尾，`data-entry-seq` 连续。
11. 回复区的展开条件：聚焦、草稿不为空、有正在进行或结果未确定的操作时展开；失焦且草稿为空时收起。
12. `tests/modules/issues/` 下现有的测试不删。断言所测的行为确实变了的，可以改，但要在交付说明里逐条列出改了哪条、为什么改。`npm test`、`npm run typecheck` 全部通过。
13. 真机：在跑的 Router 读到新页面之后（时机归用户），在本机浏览器打开一个长议题，确认第 1、2、4、7 条的现象，并记入 `docs/manual-tests.md`。

## 六、验证方法与变异检验

- 真实浏览器测试用仓里已有的 `@playwright/test`（1.64.1）启动 chromium，写法参照 `tests/graph-browser.mjs`。happy-dom 没有布局，算不出高度和滚动，所以第 1–8 条不能用它代替。本机目前没有 `%LOCALAPPDATA%\ms-playwright` 目录，跑之前先确认 chromium 已经装好。
- `tests/graph-browser.mjs` 读的是 `dist/`。新测试要么直接从 `src/` 起服务（vitest 可以直接跑 TS），要么在自己的工作树里 build。不要在主检出 build：在跑的 Router 每次请求都会读页面。
- 不碰在跑的共享 Router（pid 见 `~/.lane-router/discovery.json`）；测试一律用临时数据目录。
- 2026-10-19 补充：浏览器测试和其他测试并发跑时会挤占 CPU，全量测试里已经让两个起进程的用例超过 5 秒上限。因此浏览器测试放进 vitest 的一个单独 project，用 `sequence.groupOrder` 排在其他测试全部跑完之后（vitest 4.1.10 支持）。这样它仍属于 `npm test`，但不再和其他测试并发。不要靠逐条放宽超时来解决。
- 变异检验（每次改坏一处，看对应的测试有没有变红，看完改回）：
  - 去掉两栏框的高度上限 → 1、3 变红
  - 把回复区挪进历史区 → 2、9 变红
  - 恢复每次轮询都用 `replaceChildren` 重建 → 4、5、10 变红
  - 打开议题时总是滚到顶 → 7 变红
  - 用标已读之后的 `readSeq` 计算首条未读 → 7 变红（会落到底部）
  - 窄屏也启用框内滚动 → 8 变红
  - 删掉跟随规则 → 6 变红

## 七、边界

- 窄屏保持现状。窄屏下选中议题后不会滚到详情，另行处理。
- 已读标记的时机和口径不改：页面仍然在渲染后就把已加载的内容标为已读，不管内容有没有进入视野。改成框内滚动后，这个差别会更明显，已作为单独事项提给用户。
- 分页方向不改：议题超过 100 条时，首屏仍是最旧的一页（见 3.4 规则 7）。
- 「回复对象」的默认值不改。网页回复没有指定问题时，原来的问题不会被标为已回答，这是另一件事。
- 在跑的 Router 什么时候读到新页面，归用户决定。
