# 停下来等用户的 lane 没有落点 —— 问题确认稿

**状态：** 问题确认稿，2026-10-14 与用户对话确认。**只写问题，不写方案**；方案另起一稿，并以本文的「边界」一节为约束。

## 一句话

> lane 停下来等我，这件事只存在于我脑子里和那个窗口里。我靠回忆和窗口堆来调度十几条 lane，它们的数量一涨，回忆的漏洞和窗口的乱都跟着涨。

## 术语表

| 词 | 含义 |
|---|---|
| 等待事件 | 一条 lane 结束一轮、停下来等用户说下一句的那个时刻 |
| 冷启动 | 回到一条 lane 时，重新弄清「这条现在在解决什么、停在哪」所付的代价。今天的做法是进窗口让 agent「remind me」，然后读 |
| 提醒板 | 让用户想起「有件事在推进」的东西。今天实际承担这个角色的是开着的窗口 |

## 现状（2026-10-14 实测与用户自述）

- 在用库里未归档 lane **58 条**，分在 **26 个项目**，全部有绑定。此刻约 **18 条**开着窗口（claude 进程 16 个、codex 2 个，按一个进程一条 lane 估）。其中 3 条在 Linux 虚拟机上（PuTTY + tmux，不在本机 Windows Terminal 的项目分组里）。
- 58 条里有若干是 campaign 制 lane（角色里写明「结论出了即归档」），目前仍未归档。
- 用户的工作方式：让一条 lane 推进 → 去别的 lane 干活 → 想起来再回来看。回来时 lane 多半已经停下在等；偶尔还在跑，那就再走开一次。
- 一天回到 lane **几次到十几次**。
- 回来的触发有四种，全在人这一侧：随机想起 / 看见窗口 / 空闲时在脑子里扫一遍「还有什么没完」/ 别人来问。
- 别人来问的情况不多，而且多半意味着新需求或要新开 lane，不是已有 lane 停着没人管。
- 隔几天才想起的情况少见（放假回来会有）；隔几小时的冷启动天天有。
- Vikunja 刚接入，用途是需求备忘。记得偏多但用户接受，因为记的是具体需求。

## 等待事件今天落在哪

| 可能的落点 | 为什么落不住 |
|---|---|
| Vikunja | 粒度不对。它记「要做什么需求」，不记「哪条 lane 现在停着等我」。一条需求可以对应几条 lane、几轮往返 |
| 看板 | 只知道忙 / 闲（Claude 侧来自 `Stop` / `UserPromptSubmit`），不知道为什么停、在等什么 |
| 用户的脑子 | 唯一真正在用的落点。「随机想起」和「空闲时扫一遍」这两种触发，都是用户在主动回忆 |
| 窗口 | 事件**也**落在这里，而且是四种触发里唯一不靠回忆的：「看见窗口想起来」 |

## 三个后果，同一个来源

| 结局 | 代价 |
|---|---|
| 想起来了 | 付一次冷启动。一天几次到十几次 |
| 没想起来 | 停住，直到随机想起或别人来问 |
| 为了能想起来 | 窗口不敢关，越堆越多，已经跨到虚拟机 |

## 边界（方案必须守的）

1. **remind 的产出质量不是问题。** 用户确认过。改 remind 写得好不好，动不了冷启动的总量。
2. **并行推进的 lane 数不是可以削的变量。** 这是工作需要，用户认为没法少。方案不能以「少开 lane」为前提。
3. **窗口是现在的提醒板。** 任何减少窗口的方案，必须先给「看见窗口想起来」找到替代，否则「没想起来就停住」会恶化。
4. **Vikunja 不是等待事件的落点，也不该被顶掉。** 需求记录仍归它；它刚启用，效果还要看。
5. **主要代价是用户自己的。** 同事在等的情况不多，且多为新需求；方案不必为「对外承诺」单独设计。
6. 回来时 lane 偶尔还在跑：这说明用户今天也不知道**等待事件什么时候发生**，只知道「大概该好了」。

## 待讨论的问题（进入方案阶段再答）

1. 等待事件该落在哪？由谁写、什么时候写？
2. 冷启动要的那句「现在在解决什么、停在哪、等什么」，该在 lane 停下来那一刻产出，还是在用户回来时产出？两者代价落在谁身上？
3. 提醒板这个角色由什么接替？接替之后窗口还需要常开吗？
4. 虚拟机上的 lane 怎么进同一个落点？
5. campaign 制 lane 做完没归档，是纪律问题还是缺一个「该归档了」的信号？
