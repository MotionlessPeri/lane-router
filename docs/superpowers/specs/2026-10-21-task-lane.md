# 任务 lane：角色 lane 为有界需求开临时 lane，做完自己归档 —— 需求与设计

**状态：** 需求与设计合一稿，2026-10-21 由 `lane-router/design` 起草；用户在问答 `25c76c8a` 定口径；impl 审稿后修订；**用户 2026-10-21 03:38 gate 通过，带一处修改**：「窗口不要我来关……父 lane 负责关掉就好了吧，其他的没啥问题」——4.3 第 4 条据此改为 Router 自动结束进程 + 父 lane 兜底命令（范围审计、验收 5 / 6 / 10 随之改）。4.3 第 4 条依赖的一项取证（外部结束空闲 claude.exe 后会话记录是否完整）见第三节末，design 在今晚的真机验收里补。Vikunja LR-27。实现：`lane-router/impl`（Router：`lane_finish`、拒收、结束进程、归档、`close`）；问答页横幅归 `inbox-impl`；规范改写归 design。依赖 LR-18（开 lane 不再先问用户）已上线。

## 一、问题与结论

用户原话：「小任务就是那种看得清边界的需求。比如我给你提了一个lane-router的小需求，需要稍微澄清几轮就可以做了，我就希望可以开一个新lane去做，特别是你在忙别的或者有并行很多个需求来的时候。做完自己归档肯定是必须的，其实这个有点对标company的那个子task。这个规范要改写一下。」「窗口不要我来关吧，我们后面会开特别多窗口，让我找太费劲了，你们直接父lane负责关掉就好了吧。」

**结论**：在 subagent 和常驻角色 lane 之间加一层**任务 lane**——为一条边界清楚、但要和用户澄清几轮或要跑一阵的需求临时开的 lane；由收到需求的角色 lane 直接开（不再先问用户），角色说明写明归属与完成条件；**做完交付后自己宣告完成，Router 在它这一回合结束时结束它的进程（窗口随之关掉）并归档它**；父 lane 另有一条兜底命令对付忘了宣告或卡死的任务 lane。用户不碰窗口。这是 Company 子 task 的对标——接过「有界责任、显式完成、做完清理」，不做账本。

## 二、术语

| 词 | 含义 |
|---|---|
| subagent | Agent 工具开的进程内子代理：一次性、不上看板、不能和用户在问答 / 邮箱里对话。 |
| 任务 lane | 为一条有界需求临时开的 lane：有地址、上看板、能和用户澄清、能被找到和唤醒；角色说明以「任务 lane：」开头；完成即归档。 |
| 角色 lane | 常驻的长期职责 lane（design / impl / inbox …）。 |
| 完成（finished） | 任务 lane 自己宣告的终态：交付已做、邮件与议题已清、不再接活、等 Router 收尾。 |
| joinKey | Claude lane 的频道连接时上报的键，就是该会话 `claude.exe` 的进程号（`src/mcp/lane-mcp-server.ts:33`：`CLAUDE_PID ?? ppid`）。 |

## 三、取证

- `archiveLane`（`src/router/router-core.ts:412-428`）对 `restorePresence === "online"` 的 lane 报 `LANE_ONLINE`；**还拒绝有未读邮件的 lane**（`router-core.test.ts`「refuses to archive a lane that still has unread messages」）；只归档离线且无未读的 lane；归档把它的邮件移出工作集、记 `archivedAt`，地址对 `new` 视为空闲。⇒ 「自己归档」要补的缺口有两处：在线时不能归档；归档前不能有未读。
- `terminal-child.ts` 只起 CLI、写状态文件，**不连 Router、收不到 hook**（impl 核实）；CLI 退出后它跟着退出（`child.once("exit")`），标签页随之关闭——所以「关窗」= 结束 claude.exe 进程。
- **Router 知道每条 Claude lane 的进程号**：joinKey 就是 claude.exe 的 pid。2026-10-21 核过两例：`join.lifecycle_received joinKey:"30044"` 对应 `lane-router/probe` gen 1 的 claude.exe 30044，`joinKey:"85572"` 对应 gen 2 的 85572。Codex 的 TUI 进程宿主不持有，没有对等信息。
- Claude 的 websocket 关闭不等于会话结束：`/mcp` 重连、MCP 进程重启都会短暂断开（impl 指出）。Codex 关掉 TUI 后宿主里 thread 仍在，没有对等的「关闭」事件（`restorePresence` 与 `reach` 有意分开）。
- 问答模块给已归档 lane 投递会报 `LANE_UNAVAILABLE`。
- 之前的临时 lane 做法（各 research lane）靠角色说明写「结论交付后归档」，但归档要人跑命令、窗口要人关——清磁盘时翻出 40 多条没人记得干嘛的 lane 和 worktree。
- LR-18 已把「开 lane 要先问用户」拆掉；LR-14 的 set description 让看板能解释一组 lane 是干嘛的。
- **待取证（design 今晚真机验收顺带做）**：对一条空闲（最近一次 lifecycle 是 `Stop`）的 Claude lane 从外部结束 claude.exe，再 `lane-router-lane open` 回来，会话记录是否完整、频道是否照常重连。结果补在这里；若记录不完整，4.3 第 4 条改为「等 Stop 后先让 lane 自己 `/exit`」之类的替代，重新过 impl。

## 四、设计

### 4.1 三层口径（进规范）

| 层 | 用在 | 开法 | 收尾 |
|---|---|---|---|
| subagent | 不需要和用户对话、不需要被找到的内部活 | Agent 工具 | 自动 |
| **任务 lane** | 边界清楚的需求，但要和用户澄清几轮、或要跑一阵、或要能被找到 / 唤醒 | 收到需求的角色 lane 直接开（4.2） | **交付 → 清邮件与议题 → `lane_finish` → Router 在回合结束时结束进程并归档** |
| 角色 lane | 长期职责 | 用户或角色 lane 开 | 用户决定归档 |

判据：先问「subagent 够不够」——能，就不开 lane。满足「要和用户对话 / 要被找到 / 要跨会话活着 / 要被唤醒」任一条才开任务 lane。首版任务 lane 只用 Claude 后端（4.3 第 4 条）。

### 4.2 任务 lane 的开法（约定，不加命令）

- 地址 `<project>/<task-slug>`；角色说明**第一句固定**：「任务 lane：为问答 `<议题 id>` 开，归属 `<父 lane 地址>`，完成条件：…，完成即归档。」后面才是任务本身。这一句同时是 4.3 里 `lane_finish` / `close` 的准入凭据。
- 父 lane 开它时在**原议题**里说一句「开了 `<地址>` 去做，原因…」；任务 lane 自己的问答归它自己。
- 可以放进父 lane 的 lane set（LR-14 description 写清这组是哪条需求的）。
- 不加 `--task` 之类的新参数：首句约定 + 看板可见就够。

### 4.3 完成与归档（Router 补的小路径）

1. **`lane_finish`**（MCP 工具 + CLI `lane-router-lane finish`；**没有地址参数**，只作用于调用者自己）。准入三条，缺一拒绝并说明原因：
   - 调用者有 active binding；
   - 调用者的角色说明以「任务 lane：」开头（`LANE_NOT_A_TASK_LANE`——角色 lane 误调一次不能把自己永久归档掉）；
   - 调用者的 mailbox 没有未处理（未 ack）邮件，且它名下的问答议题没有 `waiting_user` / `waiting_lane`（`LANE_FINISH_BLOCKED`，错误信息列出还剩什么）——先清干净再完成。
   通过后记 `finished_at = now`（lanes 表新增可空时间戳，schema 11 → 12，按现有迁移写法）。
2. **finish 之后拒收**：对 `finished_at` 非空的 lane，`lane_send`、问答投递、`tell` 一律拒绝，错误 `LANE_FINISHED`，信息里带它角色首句里的原议题与父 lane（「该任务 lane 已完成；追问请到问答 `<议题>` 或联系 `<父 lane>`」）。这样归档前不会再堆出未读信。
3. **归档时机**：
   - Claude 后端：频道关闭后**等 30 秒宽限**，再核 `restorePresence`；仍离线且 `finished_at` 非空且无未读 ⇒ `archiveLane`。宽限是为了 `/mcp` 重连、MCP 重启这类短暂断开——finished 的 lane 若重连上来，仍可读信（只读）和再次 finish，不会被误杀。
   - Codex / zcode / dsh：没有对等的关闭事件，**靠 reconcile**——Router 启动与每次 reconcile 时，凡 `finished_at` 非空、`restorePresence` 非 online、无未读的 lane 归档。Claude 的也在 reconcile 兜底。
   - 若归档前发现仍有未读（理论上只剩 finish 与拒收之间的极小竞态）：不归档，看板标「已完成，有 N 封未读」，下次 reconcile 或收到 ack 后再判。
4. **关窗：Router 做，用户不碰。**
   - Claude 后端：`lane_finish` 通过后，Router 记下该会话的 joinKey（claude.exe pid）；**等到该会话下一次 `Stop`**（`lane_finish` 本身是在回合里调的，回合结束才算记录写完），结束这个进程（`process.kill(pid)`，Windows 上即 TerminateProcess）；terminal-child 随 CLI 退出而退出，标签页关闭；频道关闭 → 第 3 条的 30 秒宽限 → 归档。进程已不在（用户先手关了）就什么都不做，走第 3 条。
   - **父 lane 兜底：`lane-router-lane close <address>`**（CLI + 本机路由，`refuseWebPage` 防护）：对付做完了却忘了喊 finish、或卡死的任务 lane。只对角色首句「任务 lane：」的 lane 有效（`LANE_NOT_A_TASK_LANE`，常驻 lane 关不掉）；对在线的目标同样等它下一次 `Stop` 再结束进程（目标已空闲——最近一次 lifecycle 是 `Stop`——则立即），对离线的目标直接归档（有未读则先按第 3 条口径标出，不归档）。`close` 不要求目标 finished：它就是给没 finish 的用的。
   - Codex 任务 lane：宿主不持有 TUI 进程，首版**不自动关窗**，看板标「已完成，待关窗」，走第 3 条的 reconcile 归档。规范写「任务 lane 先只用 Claude 后端」；Codex 的自动关窗另起小稿。
5. **归档后的问答**：任务 lane 名下的议题保留（历史），页面给所属 lane 已归档的议题加一条横幅：「该任务 lane 已完成归档；追问请到父 lane 的议题 `<id>`，或让父 lane 再开一条任务 lane」，回复框禁用（inbox-impl，一小处）。

任务 lane 的收尾顺序固定：交付（按授权提交 / 交集成者 / 在问答里报结果与产物位置）→ 在原议题回一句「完成，产物在…」→ 处理并 ack 剩余邮件、把自己的议题答完或关闭 → `lane_finish` → 不再调任何工具、结束这一回合 → Router 收尾。

## 六、验收标准

自动测试：

1. `lane_finish` 的 schema **没有地址参数**（schema 测试）；有 active binding、角色首句为「任务 lane：」、无未处理邮件、名下议题无悬而未决的调用者 → `finished_at` 非空；角色首句不是「任务 lane：」→ `LANE_NOT_A_TASK_LANE`；有未 ack 邮件或有 `waiting_*` 议题 → `LANE_FINISH_BLOCKED` 且信息列出剩余项；无绑定 → 拒绝。
2. finished 的 lane 收 `lane_send` / 问答投递 / `tell` → `LANE_FINISHED`，信息含原议题与父 lane；未 finished 的照常。
3. Claude 频道关闭：finished 的 lane 30 s 后仍离线且无未读 → 归档（`archivedAt` 非空、邮件移出工作集、地址对 `new` 空闲）；30 s 内重连 → 不归档；未 finished 的 lane 频道关闭 → 不归档。
4. reconcile：`finished_at` 非空、`restorePresence` 非 online、无未读的 lane 被归档（含 Codex 后端夹具）；在线的、有未读的不动，后者在快照里标「已完成，有 N 封未读」。
5. 结束进程（用可注入的 killer 夹具记录被杀的 pid）：Claude lane `lane_finish` 通过后、同一回合内 **不**杀；收到该会话的 `Stop` 后杀 joinKey 对应的 pid，且只杀一次；finish 时进程已不在 → 不报错、走归档；Codex lane finished → 不调 killer，快照标「已完成，待关窗」。
6. `close`：目标角色首句不是「任务 lane：」→ `LANE_NOT_A_TASK_LANE`；目标在线且空闲 → 立即杀；在线且回合中 → 等 `Stop` 再杀；目标离线无未读 → 直接归档；离线有未读 → 不归档、标出未读数；本机路由带 Origin → 拒绝。
7. 既有 archive、reconcile、lane-access、问答投递测试全过；schema 11 → 12 升级测试通过，旧库升级后数据不变。
8. `npm test`、`npm run typecheck` 全过。

浏览器（issues 组）：

9. 所属 lane 已归档的议题显示横幅与父议题链接，回复框禁用。

真机：

10. 用一条真实小需求走全程：角色 lane 在原议题说明后开任务 lane → 任务 lane 与用户在问答澄清 → 交付 → 原议题回报 → 清邮件、关自己议题 → `lane_finish` → 这一回合结束后它的窗口自己关掉（用户没碰）→ 30 s 后 `lane-router-lane list-archived` 看到它、看板不再显示；给它发信得到 `LANE_FINISHED`。再对一条故意不 finish 的任务 lane 由父 lane 跑 `lane-router-lane close`，窗口关掉、归档。记 `docs/manual-tests.md`。
11. 规范 `:80 / :83 / :85 / :199` 为三层 + LR-18 口径（已改），工具表含 `lane_finish`、开窗一节含 `close`；`scripts/kb/kb.py lint` 不报错。

## 七、验证方法与变异检验

- 跑法：`npm test`、`npm run typecheck`；主检出不 build。
- 变异：去掉「任务 lane：」首句准入 → 1、6 红；去掉未读 / 议题检查 → 1 红；finished 仍收信 → 2 红；去掉 30 s 宽限（关闭立即归档）→ 3「重连不归档」红；关闭不看 `finished_at` 就归档 → 3 红；reconcile 不处理 finished → 4 红；`finished_at` 不持久 → 4 红；归档绕过既有逻辑（不移邮件）→ 3 红；finish 当场就杀 → 5「同一回合内不杀」红；Stop 后不杀 → 5 红；对 Codex 也杀 → 5 红；`close` 不看首句 → 6 红；`close` 回合中就杀 → 6 红。

## 八、边界

- 只加一个自用的 `finish`、一列、一个带宽限的关闭钩子、reconcile 一条规则、一个拒收错误、「Stop 后结束 joinKey 进程」一条规则、一条 `close` 命令 + 本机路由、一条页面横幅；不加父子关系、不加账本、不加 `new` 的参数、**不动 terminal-child**（结束进程由 Router 做，pid 来自已有的 joinKey）。
- Codex 自动关窗、worktree 自动清理：推迟，各自另起小稿。
- 上线：改了工具目录（`lane_finish` 进 catalog），**要带 `-CodexHost`**；Claude 侧新开 / 恢复会话生效。可与 LR-28「切号后继续」一批（那批还要重启账号后台）。
