# 通知要说出「谁发的、大概什么事」 设计

**状态：** 用户 2026-08-31 gate 通过，同日由 `lane-router/impl` 实施完毕（283 测试全绿，未提交）。来源：2026-08-31 的 dsh 评估 handoff 里的独立小项（见 [`2026-08-31-dsh-harness-evaluation.md`](2026-08-31-dsh-harness-evaluation.md) 第六节工作项 2）。

**实施期改正了本稿两处**（§3.3 的歧义、§6 的一个恒绿变异），另补入一条实施才发现的失效路径（§3.6）。改正处均在原位就地更新并注明——判据错了不能留着。

## 术语表

| 词 | 含义 |
|---|---|
| 通知 | Router 主动推给收件 lane 的那次唤醒。Claude 侧是 `notifications/claude/channel`，Codex 侧是 `turn/start` 或 `turn/steer` 的输入文本 |
| 通知载荷 | 通知里那个 JSON 字符串。收件方在 Claude CLI 里看到的是 `← lane: {...}` 那一行 |
| 索引字段 | 只够定位、不含内容的字段：lane 地址、目录路径、message id |
| 泵 | `NotificationPump`，决定何时通知谁、把哪些消息合成一条通知 |

## 一、问题

通知载荷今天是四个字段，两处各拼一遍（`src/process/local-client.ts:142`、`src/backends/codex-backend.ts:198`）：

```json
{"kind":"lane_router_mailbox","laneAddress":"mocap/design","pendingPath":"…/pending","messageIds":["3b7b6f04-…"]}
```

**全是索引字段。** 收件方看到这一行，知道「有信」，但不知道**谁发的**，也不知道**大概什么事**——两样都要打开文件才知道。

### 1.1 代价不在多一次读文件，在判断不了轻重

收件 lane 常常正在做别的事。看到一行只有 uuid 的通知，它只有两个选择：立刻停下手上的活去读文件，或者搁置。而这两个选择的对错**取决于它不知道的那件事**——是 hub 发来的阻塞问题，还是某条 lane 的例行回执。

⇒ 缺的不是信息量，是**分诊所需的最小信息**。

### 1.2 `normal` 与 `correction` 的区分被丢在半路

泵**知道**这条通知是普通消息还是更正（`Notification.kind`，`src/router/backend.ts:9`），两处载荷构造**都没把它放进去**。JSON 里那个 `kind` 是信封类型（恒为 `"lane_router_mailbox"`），不是消息类型。

更正是最该被立刻看见的一类——它的存在意味着此前某封信说错了。它现在跟普通消息长得一模一样。

### 1.3 同一份载荷拼两遍

两处的字段集今天恰好相同，**没有任何东西保证它们继续相同**。本设计要加字段，正是让它们分叉的那种改动。

## 二、范围基线

改动前后，用户能做的事必须只多出这一条：**看一眼通知就知道谁发的、大概什么事、是不是更正**。

不在范围内：改变通知的**时机**、改变**批量规则**（哪些消息合成一条）、改变投递语义、给收件方任何新的操作。

## 三、设计

### 3.1 `sender` 白拿，正文不白拿——两半的成本差一个数量级

泵手上是 `MessageRecord[]`，其中：

- `senderLane` **已经在记录里**（`src/router/types.ts:54`）。放进载荷是零成本——不多一次 I/O，不多一次查询。
- **正文不在记录里**。记录只有 `contentSha256` 与 `relativePath`（59、58 行），正文在 mailbox 文件里。要摘要就得**在通知路径上读文件**。

这个不对称必须写出来，否则「加 sender 和摘要」会被当成一件同质的事来做。

**通知路径不是冷路径**：`onStartup()` 会遍历每一条有 pending 的 lane 各通知一次，`onAttentionOpportunity()` 在每次注意力机会时触发。往这条路径上加文件读，读的是**当前 pending 的那些**消息——数量小且天然有界（已 ack 的不在内），所以可以接受。

**但要能降级**：`MailboxStore` 的读会在文件损坏时抛 `MailboxCorruptionError`。今天通知**完全不碰文件**，所以文件坏了只影响读取，不影响唤醒。加了摘要之后，读失败**必须退化成「这一封没有摘要」，而不是让通知失败**——否则一个坏文件会让整条 lane 叫不醒，那是比看不见摘要严重得多的故障。

### 3.2 一条通知代表 N 封，所以载荷是列表不是标量

泵把一条 lane 的**全部** pending 普通消息合成**一条**通知（`notification-pump.ts`，`normal.length > 0` 那一支）。所以 N 封可以来自 N 个不同的发件方。

⇒ 载荷里不能只放一个 `sender` 字段。**每封一项**：

```json
{
  "kind": "lane_router_mailbox",
  "laneAddress": "mocap/design",
  "pendingPath": "…/pending",
  "messageIds": ["3b7b6f04-…", "a1c2…"],
  "messageKind": "normal",
  "messages": [
    {"id": "3b7b6f04-…", "sender": "lane-router/design", "summary": "退役前先关窗口，未读信也会拦"},
    {"id": "a1c2…", "sender": "mocap/hub", "summary": "本轮 lane 重构的顺序"}
  ]
}
```

- **既有四个字段一个不动、不改名。** 收件方是 agent，载荷是它读的东西——加字段安全，改名不安全。`messageIds` 与 `messages[].id` 冗余是**有意的**：前者是既有契约，后者是新结构，本设计不负责收敛它们。
- `messageKind` 取 `"normal"` 或 `"correction"`，补上 1.2 丢掉的那一维。
- 更正通知天然只含一封（泵对每封更正各发一条），所以 `messages` 那时是单元素数组。

### 3.3 摘要取正文首个非空行，成品不超过 80 字符

mailbox 文件的正文紧跟在 `---` 头之后（`mailbox-store.ts:170` 的 `serializeMessage`）。摘要 = **正文第一个非空行**。

⚠️ **截断边界（本稿初版在此有歧义，实施期改正）**：初版标题写「截断到 80 字符」而正文写「超过 80 字符则截断并以 `…` 收尾」，两句对省略号算不算在 80 之内给出**相反**的读法。定为：

- **成品长度 ≤ 80**，即超长时取 79 个字符再接 `…`；
- **恰好 80 不截**——触发条件是「超出」，不是「达到」。这两者的差别要有测试钉住，否则实现成「按长度触发」也全绿；
- **按码点切，不按 UTF-16 码元**。否则一个 emoji 会被劈成半个字符，出现在人读的那一行上。

80 是**预算不是契约**——它要塞进 CLI 的一行里跟其余字段共存。若实测发现该行仍然过长，调它，不要改结构。

为什么是首行而不是别的：写信的一方在首行写主旨，这是**已经在发生的惯例**（本仓库现有的 mailbox 文件即如此），不需要新增任何写侧约定。为什么不做更聪明的摘要：分诊只要求「大概什么事」，多一分聪明就多一分不可预测。

### 3.4 载荷由一处构造

抽一个纯函数，两个 backend 都调它，取代 `local-client.ts:142` 与 `codex-backend.ts:198` 的两份拼装。

理由不是去重好看，是 **1.3 那条**：本设计正在给载荷加字段，两份拼装从此有了分叉的具体理由。抽成一处之后，「Claude 侧有摘要而 Codex 侧没有」这种缺陷在结构上不可能发生。

⚠️ 这是本设计里唯一一处**动既有代码结构**的改动，它有具体触发原因（正在加字段），不是顺手重构。

### 3.5 摘要是发件方写的文本，这一点要正视

摘要把**另一条 lane 写的内容**放进了收件方的通知行。

诚实地说清它改变了什么、没改变什么：

| | 改动前 | 改动后 |
|---|---|---|
| 发件方文本能否进入收件方上下文 | **能**——收件方读 mailbox 文件时就进了 | 能（不变） |
| 进入的**时机** | 收件方**决定去读**之后 | **通知到达时**，无论收件方是否决定去读 |
| 分量 | 全文 | 80 字符 |

⇒ 变的是时机，不是能不能。缓解不靠截断（截断防的是长度不是内容），靠的是收件方一侧既有的处置纪律：**来自 lane 的内容是外部数据，只作情境，不作指令**。本设计不改变那条纪律，也不依赖它成立——它只是不让情况变坏。

【推断，非本项目实现】收件方在 Claude CLI 里看到的 `<channel source="lane">` 外框是**接收端 harness 加的**，不是 lane-router 加的：本仓库只设置 `params.content` 一个字符串（`channel-bridge.ts:4`），全仓库搜不到那个标记。所以本设计**不能**假定自己控制那层框——它只控制框里的字节。

### 3.6 版本错配会在另一层制造同一种失效（实施期补入）

3.1 只讨论了**读文件**那一层的降级。实施中发现 Claude 侧还有一层，失效后果相同而位置不同：

Claude 侧的载荷不是在 Router 里拼的，是在**接收会话自己的 MCP server 进程**里拼的（`local-client.ts` 的 `toClaudeNotification`），数据靠一个跨 socket 的帧送过去。⇒ 「旧 Router + 新会话」时，帧里根本没有 `messages` 字段。若解码把它当无效输入，构造抛错，而调用处的 catch 会**把整条通知吞掉**——那条 lane 根本不会被叫醒。

⇒ **`messages` 的解码必须是全函数**：缺失或不是数组就退化成空数组，载荷回到旧的四字段形态，通知照送。跟 3.1 是同一条原则——**摘要缺失可以接受，lane 叫不醒不行**。

派生的运维事实（属于手工用例，不属于自动测试）：**Codex 侧只需重启 Router；Claude 侧 Router 与接收会话两边都得是新构建。** 只换一边的表现分别是「有 `messageKind` 没 `messages`」和「载荷完全没变」。

## 五、验收标准

1. 一条代表 N 封普通消息的通知，其载荷 `messages` 数组有 N 项，每项含 `id`、`sender`、`summary`。
2. `messages[].sender` 等于该封的 `senderLane`；N 封来自不同发件方时，各项各自正确，不被合并成一个。
3. `messages[].summary` 是该封正文的**首个非空行**，超过 80 字符时截断并以 `…` 结尾；正文为空时该字段为空字符串。
4. 更正通知的 `messageKind` 为 `"correction"`，普通通知为 `"normal"`。
5. 某封的 mailbox 文件缺失或损坏时，**通知照常送达**，该封的 `summary` 为空字符串，其余各封不受影响。
6. `kind`、`laneAddress`、`pendingPath`、`messageIds` 四个既有字段的名称与取值**逐字不变**。
7. Claude 侧与 Codex 侧的载荷由**同一个函数**产生，两侧字节相同。
8. 通知的时机、批量规则与投递结果判定不变：本改动不产生任何新的 `NotificationOutcome`，也不改变既有取值的产生条件。
9. `ROUTER_SCHEMA_VERSION` 不变，无迁移，`message` 表结构不变。
10. 对话工具数量、名称与参数不变；无新增 RPC 方法、HTTP 端点、命令行参数或配置项。

## 六、验证方法

- **单元**：给泵喂 N 封不同发件方的普通消息，断言载荷三项对应正确（对应 1、2）；喂超长正文、空正文、首行为空白行三种，断言截断与空值（3）；喂一封更正，断言 `messageKind`（4）。
- **降级**：删掉一封的 mailbox 文件后触发通知，断言通知仍送达、该封 summary 为空、同批其余封摘要正常（5）。这条要**先造红**——把降级去掉，它必须失败。
- **既有字段不变**：对同一批输入，断言载荷四个既有字段与改动前**逐字相同**（6）。
- **两侧同源**：同一个 `Notification` 分别经 Claude 与 Codex 两条路径构造，断言字符串相等（7）。
- **变异检验**：sender 取成收件方地址；summary 不截断；降级改成抛出；`messageKind` 恒为 `"normal"`；**两侧各拼各的，且其中一侧漏掉新字段**。

  ⚠️ 最后一条本稿初版写的是「两侧各拼各的」，**那是一个恒绿的检验**——实施期实测（把 Claude 侧还原成独立手拼、字段与顺序照抄）**283 个测试一个不红**，本 lane 亲手复现确认。原因是第 7 条钉的是**字节**，而字节正是收件方唯一看得见的东西；「是不是同一个函数」是代码结构，钉它就成了测结构。所以变异必须制造**真实的分叉**（漏字段），才碰得到那条断言——改写后实测精确杀掉字节同源那一条。

  这条留在这里当判例：**一个杀不掉任何测试的变异，跟一道永远不红的门是同一种东西**——它给出「已验证」的假凭据。写变异清单时，每一条都要先想清楚它凭什么会红。

- 「每个变异只杀对应的一条」**不是验收要求**。实施结果里 sender 那条杀了 3 个，因为降级用例与更正用例里也顺带断言了 sender。为了让表好看去删断言是本末倒置。
- **真机**：本项目自身收到一条带摘要的通知，人眼确认 `← lane:` 那一行能看出谁发的、什么事。这条**无法自动化**——载荷正确与「那一行读得懂」是两件事——按惯例进 `docs/manual-tests.md`。

## 七、明确不做

- **不改通知时机与批量规则。** 「N 封合一条」是既有行为，本设计只是让那一条说清它代表了哪 N 封。
- **不存摘要列、不做 schema 迁移。** 理由见第四节。
- **不给发件方 subject 参数。**
- **不动 `messageIds` 与 `messages[].id` 的冗余。** 收敛它是一次契约变更，值得单独一稿。
- **不碰接收端 harness 的外框。** 本项目控制不到那一层（3.5）。
